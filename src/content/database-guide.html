Section 01

Choosing the Right Database

Default to a relational database unless the requirements give you a clear reason not to. This mirrors the API cheat sheet's protocol advice for a reason. In both cases, interviewers are testing judgment, not encyclopedic knowledge of every option.

Type Best For Signals to Listen For Avoid When
Relational (SQL) Structured data, relationships, transactions Orders, payments, users, anything needing joins or consistency Schema changes constantly, data is naturally a document
Document (NoSQL) Semi-structured, nested, evolving data Product catalogs, CMS content, user profiles with varying fields Heavy cross-entity relationships and joins
Key-Value Simple lookups by ID, extreme speed Session storage, caching, feature flags You need to query by anything other than the key
Wide-Column Massive write throughput, time-series IoT sensor data, event logging, metrics at huge scale Small datasets, complex ad-hoc queries
Graph Relationships ARE the data Social networks, recommendation engines, fraud detection Data is mostly tabular with few relationships

Quick Decision Rule: Which Database Type?

  1. Does the data have clear structure and relationships? Use relational (SQL).
  2. Does the schema change often, or is data naturally nested? Consider a document store.
  3. Do you only ever look things up by a single key, at huge scale? Consider key-value.
  4. Is the question "who is connected to whom, and how"? Consider graph.
  5. Is write volume the dominant constraint, more than query flexibility? Consider wide-column.
Interview Tip. Do not open with "SQL vs NoSQL" as a binary. Say "I will start with PostgreSQL because the data has clear entities and relationships, and I need transactional guarantees on orders. If read scale becomes the bottleneck later, I would add a cache or a read replica before reaching for a different database entirely." This shows you reach for the boring, well-understood option first.
Extra Interview Tip: NoSQL is not one thing. Say "NoSQL is not a category with one tradeoff. A document store, a key-value store, and a graph database solve completely different problems. I would pick based on the access pattern, not because NoSQL sounds more scalable." This single sentence separates candidates who have shipped real systems from those repeating a 2015-era blog post.

What Interviewers Usually Want to Hear

  • You default to relational unless there is a specific reason not to
  • You know NoSQL is a family of different tradeoffs, not one option
  • You tie the choice to the access pattern, not to a trend
  • You are willing to combine types, SQL as source of truth and Redis as cache, rather than picking exactly one

Good default: relational for the source of truth, specialize into document/key-value/graph only where the access pattern clearly demands it.

Section 02

Relational Modeling and Normalization

Normalization is about eliminating redundancy so updates only need to happen in one place. Denormalization is the deliberate, informed reversal of that. Trading redundancy for read speed. Both are tools, not a moral hierarchy.

2.1 The Normal Forms, Practically

Form Rule Fixes
1NF Every column holds a single, atomic value No comma-separated lists crammed into one column
2NF Every non-key column depends on the whole primary key Removes partial dependencies in composite-key tables
3NF Every non-key column depends only on the key, not on other non-key columns Removes transitive dependencies (e.g. storing city AND zip when zip determines city)

In practice: most production schemas target 3NF and stop. Higher normal forms (BCNF, 4NF, 5NF) exist but rarely come up outside academic settings.

Normalization example 
-- Un-normalized: city is redundant, repeated per order, and can drift out of sync
orders(id, customer_name, customer_city, customer_zip, item, price)

-- Normalized to 3NF: customer data lives once, orders reference it
customers(id, name, city, zip)
orders(id, customer_id REFERENCES customers(id), item, price)

2.2 When to Denormalize

Denormalization means intentionally duplicating data to avoid expensive joins on hot read paths. It is not a mistake. It is a tradeoff you make explicitly, after normalizing first.

Quick Decision Rule: Normalize or Denormalize?

  1. Designing the schema from scratch? Normalize to 3NF first, always.
  2. A specific read path is slow due to repeated joins? Denormalize that specific path, do not rewrite the whole schema.
  3. Data changes frequently and consistency matters? Stay normalized. Duplication risks drift.
  4. Data is written once and read constantly (analytics, feeds)? Denormalize freely.
Interview Tip. Say "I would normalize the schema first to avoid update anomalies, then denormalize specific hot read paths once I have evidence a join is actually the bottleneck. Not preemptively." This shows you do not treat denormalization as a starting point, which is a common junior mistake.
Extra Interview Tip: bring up materialized views. Say "Instead of denormalizing the actual schema, I could use a materialized view that pre-joins and pre-aggregates the data, refreshed on a schedule or on write. That gives me fast reads without duplicating source-of-truth data." This is the answer that shows you know a third option exists between "always join" and "duplicate everything."

What Interviewers Usually Want to Hear

  • You can explain 1NF/2NF/3NF in plain terms, not just recite definitions
  • You normalize by default and denormalize with evidence, not by instinct
  • You know materialized views as a middle-ground option
  • You understand denormalization's real cost: data can drift out of sync

Good default: normalize to 3NF, denormalize only specific proven-slow read paths, consider materialized views before duplicating source data.

Section 03

Indexing

An index is a separate data structure that lets the database find rows without scanning the entire table. It trades write speed and storage for read speed. Every index you add makes every write slightly slower, because the index has to be updated too.

3.1 Index Types

Type How It Works Best For
B-Tree Balanced tree, sorted, O(log n) lookup Default index type: equality, range queries, sorting
Hash Direct key-to-location mapping, O(1) lookup Exact-match lookups only, no ranges or sorting
Composite Index across multiple columns, in a specific order Queries that filter or sort on multiple columns together
Covering Index includes every column the query needs Lets the database answer entirely from the index, skipping the table
Full-Text Inverted index over word tokens Text search: "contains," not just "equals"

3.2 The Composite Index Column-Order Rule

This is the most commonly missed indexing detail in interviews. A composite index on (user_id, created_at) can efficiently serve queries filtering on user_id alone, or on user_id AND created_at together. But it cannot efficiently serve a query filtering on created_at alone. The leftmost column must be part of the query for the index to help.

Leftmost prefix in action 
CREATE INDEX idx_user_created ON orders(user_id, created_at);

-- Fast: uses the index
SELECT * FROM orders WHERE user_id = 42;
SELECT * FROM orders WHERE user_id = 42 AND created_at > '2026-01-01';

-- Slow: created_at alone cannot use this index, full scan instead
SELECT * FROM orders WHERE created_at > '2026-01-01';

Quick Decision Rule: Which Index Type?

  1. Equality, range, or sort on a single column? Default B-tree.
  2. Filtering or sorting on multiple columns together? Composite, most selective column first.
  3. Need exact-match only, blazing fast? Hash index.
  4. Need to search text content, not just match exact values? Full-text or trigram index.
Interview Tip. If asked to speed up a slow query, do not jump straight to "add an index." Say "First I would run EXPLAIN to see whether it is doing a full table scan, then add an index matching the actual WHERE and ORDER BY columns, with the most selective column first in a composite index." Naming EXPLAIN shows you diagnose before prescribing.
Extra Interview Tip: mention index selectivity. Say "An index on a boolean column like is_active is nearly useless. With only two possible values, the database often decides a full scan is cheaper than using the index. Indexes pay off most on high-cardinality columns, where the value narrows the result set a lot." This is a real optimizer behavior most candidates never mention.

What Interviewers Usually Want to Hear

  • You know indexes trade write speed for read speed, not free performance
  • You know composite index column order matters: leftmost-prefix rule
  • You diagnose with EXPLAIN before adding indexes blindly
  • You understand selectivity: low-cardinality columns do not benefit much

Good default: index based on real query patterns from EXPLAIN output, put the most selective column first in composites, and resist indexing every column "just in case."

Section 04

Transactions and ACID

A transaction groups multiple operations so they succeed or fail as one unit. ACID is the set of guarantees a proper transactional database makes about that unit.

4.1 The Four Guarantees

Letter Guarantee Plain English
Atomicity All operations succeed, or none do No half-finished transfer where money leaves one account but never arrives in the other
Consistency Every transaction moves the database from one valid state to another Constraints, foreign keys, and rules are never violated, even mid-transaction
Isolation Concurrent transactions do not see each other's uncommitted changes Two people booking the last seat cannot both succeed
Durability Once committed, it survives a crash A confirmed payment does not vanish if the server reboots a second later

4.2 Isolation Levels and the Anomalies They Prevent

Level Prevents Allows
Read Uncommitted Nothing Dirty reads: you see another transaction's uncommitted changes
Read Committed Dirty reads Non-repeatable reads: same query, different results, within one transaction
Repeatable Read Dirty reads, non-repeatable reads Phantom reads: new rows matching your WHERE clause appear mid-transaction
Serializable All of the above Nothing, but at the highest performance cost. Transactions behave as if run one at a time.
Transactional transfer with row lock 
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- locks the row
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

Quick Decision Rule: Which Isolation Level?

  1. Default, most workloads? Read Committed. The default in Postgres and most databases.
  2. Reading the same data multiple times within one transaction and it must not change? Repeatable Read.
  3. Financial transfers, correctness is non-negotiable, some throughput cost is fine? Serializable.
  4. High contention on a single row (limited inventory)? Pessimistic locking regardless of isolation level.
Interview Tip. When asked about a double-booking or overselling scenario, name the isolation issue directly. Say "Two requests could both read stock=1 before either writes, and both succeed. That is a race condition from insufficient isolation. I would use SELECT FOR UPDATE to lock the row, or an atomic UPDATE ... WHERE stock > 0 that fails cleanly if someone else already took the last unit." This is one of the highest-signal answers in database interviews because it is a real, common bug.
Extra Interview Tip: mention optimistic vs pessimistic locking. Say "For low-contention resources I would use optimistic locking, a version column checked on write, retry on conflict, because it avoids holding locks. For high-contention resources like concert tickets, I would use pessimistic locking with SELECT FOR UPDATE, because retry storms under heavy contention are worse than just waiting for the lock." Naming both, and when each applies, is a strong senior signal.

What Interviewers Usually Want to Hear

  • You can explain all four ACID letters in plain language, not just expand the acronym
  • You know the isolation levels and the specific anomaly each one fixes
  • You can spot a race condition in a described scenario (overselling, double-booking)
  • You know optimistic vs pessimistic locking and when each fits

Good default: Read Committed for most workloads, row-level locking (SELECT FOR UPDATE) for high-contention writes, Serializable only when correctness must be airtight.

Section 05

NoSQL Data Models

"NoSQL" describes several unrelated data models that happen to share one trait: they relax the relational model's structure or guarantees in exchange for something else. Know each one by its actual tradeoff.

Model Shape Example DBs Real Tradeoff
Document JSON-like nested objects, flexible schema MongoDB, Firestore Easy to evolve schema, but cross-document joins are awkward and often done in application code
Key-Value Simple key to value, no query language beyond the key Redis, DynamoDB Extremely fast and simple, but you must know the key. No arbitrary querying.
Wide-Column Rows with dynamic, sparse columns, optimized for writes Cassandra, HBase, Bigtable Massive write throughput and horizontal scale, but query flexibility is limited to how data was partitioned
Graph Nodes and edges, relationships are first-class data Neo4j, Amazon Neptune Traversing relationships is fast regardless of depth, but simple tabular reporting is awkward

5.1 Schema Design in a Document Store

The relational instinct is to normalize. Document stores often invert this: embed related data that is always read together, and reference data that is large, shared, or updated independently.

Embed vs reference in a document store 
// Embed: order items are always read with the order, rarely queried alone
{
  "order_id": "o_123",
  "items": [{"sku": "A1", "qty": 2}, {"sku": "B2", "qty": 1}],
  "customer": { "id": "c_45", "name": "J. Rivera" }   // small, embedded snapshot
}

// Reference: customer's full profile is large and updated independently of any one order
{
  "order_id": "o_123",
  "customer_id": "c_45"   // reference only, fetch separately if full profile needed
}

Quick Decision Rule: Embed or Reference?

  1. Read together 100% of the time, and small? Embed.
  2. Updated independently of the parent? Reference.
  3. Could grow unbounded (comments, line items)? Reference, to keep the parent document size bounded.
  4. Queried alone as often as with the parent? Reference. Avoid forcing a full parent load.
Interview Tip. If pushed on "why not just use MongoDB for everything," say "A document store shines when each entity is mostly self-contained and read as a whole, like a product page or a CMS article. Once I need strong consistency across entities, like inventory counts affecting order validity, I would reach for a relational database instead." This shows the choice follows the access pattern, not a trend.
Extra Interview Tip: modern relational databases blur this line. Say "Postgres has a native JSONB column type with indexing support, so I can get document-style flexibility for one or two fields without giving up ACID transactions and joins for everything else. I do not always need to choose a separate database just for flexible schema on part of the data." This is a genuinely underused option most candidates do not mention.

What Interviewers Usually Want to Hear

  • You treat NoSQL as several distinct models, not one alternative to SQL
  • You know when to embed vs reference in a document store
  • You know graph databases are for when relationships ARE the query
  • You know JSONB and hybrid columns can avoid needing a second database entirely

Good default: pick the NoSQL model that matches the access pattern specifically, and consider a hybrid JSONB column in Postgres before reaching for an entirely separate database.

Section 06

CAP Theorem and Consistency

The CAP theorem is frequently misquoted as "pick two of three." The more accurate and more interview-useful version: partition tolerance is not optional in any real distributed system, because networks fail. So the real choice is between consistency and availability, and only during an actual network partition.

CP or AP is the real choice, and only relevant while the network is actually partitioned.

Choice Behavior During a Partition Example Systems
CP (Consistency + Partition Tolerance) Rejects requests it cannot guarantee are consistent. Some nodes become unavailable. Traditional RDBMS with synchronous replication, MongoDB (default config), Zookeeper
AP (Availability + Partition Tolerance) Keeps serving requests from every node, may return stale or conflicting data Cassandra, DynamoDB, CouchDB

Quick Decision Rule: CP or AP?

  1. Money, inventory, anything where being wrong is worse than being unavailable? CP.
  2. Social feed, likes, view counts: staleness is barely noticeable? AP.
  3. Need both per use case? Use different databases for different data. It is normal to mix.
Interview Tip. Say "CAP only matters during an actual network partition, which is rare but must be planned for. Outside a partition, you can have both consistency and availability. The real question is: when the network splits, does this system reject writes to stay correct, or does it keep accepting writes and reconcile later?" This corrects the common oversimplified "pick two" framing, which is a strong differentiator.
Extra Interview Tip: bring up eventual consistency and its practical mitigations. Say "An AP system might briefly show a stale value, but most use techniques like read-your-writes consistency, so a user always sees their own recent write even if other users see it a moment later. That is usually enough. Most products do not actually need global strong consistency on every read." This shows nuance beyond "eventual consistency is scary."

What Interviewers Usually Want to Hear

  • You know partition tolerance is not a real choice. Networks fail, period.
  • You frame CAP as a decision that only activates during an actual partition
  • You can name CP vs AP examples and justify which fits a given feature
  • You know eventual consistency has practical mitigations, not just "it is eventually right"

Good default: CP for money and inventory, AP for social and engagement features, and it is normal to use different databases for different parts of the same product.

Section 07

Replication

Replication copies data across multiple nodes for durability and read scale. The pattern almost every interview expects by default is leader-follower (also called primary-replica).

7.1 Leader-Follower Replication

All writes go to one leader node. The leader propagates changes to one or more follower nodes, which serve read traffic. This scales reads horizontally without touching write capacity.

Mode How It Works Tradeoff
Synchronous Leader waits for follower(s) to confirm before acknowledging the write Strong consistency, but write latency increases and a slow follower slows every write
Asynchronous Leader acknowledges immediately, replicates in the background Fast writes, but a crash right after commit can lose the most recent writes on followers
Semi-Synchronous Waits for at least one follower to confirm, not all A practical middle ground used by most production systems

Quick Decision Rule: Which Replication Mode?

  1. Durability is the top priority (financial data)? Synchronous, accept the latency cost.
  2. Low write latency matters more than zero data loss risk? Asynchronous, monitor replication lag.
  3. Most production systems? Semi-synchronous. One follower confirms, others catch up async.
  4. Multi-region with local writes? Multi-leader or leaderless, plan for conflict resolution.
Interview Tip. Say "I would put reads on followers to scale horizontally, keep all writes on the leader, and specifically route a user back to the leader right after they write, so they do not see their own change disappear due to replication lag." That last clause is the part that shows real production experience.
Extra Interview Tip: mention multi-leader and leaderless replication as advanced alternatives. Say "Multi-leader replication lets multiple regions accept writes locally for lower latency, at the cost of needing conflict resolution when the same record is written in two places at once. Leaderless replication, like Dynamo-style quorum writes, avoids a single point of failure entirely but pushes consistency tradeoffs into read/write quorum tuning." Most candidates only know leader-follower exists. Naming the alternatives is a clear differentiator.

What Interviewers Usually Want to Hear

  • You default to leader-follower and know why writes stay on one node
  • You know sync vs async replication tradeoffs, and that most systems use a hybrid
  • You have named the read-your-writes problem without being prompted
  • You are aware multi-leader and leaderless replication exist as alternatives

Good default: leader-follower with semi-synchronous replication, reads scaled across followers, writes routed for read-your-writes consistency where it matters.

Section 08

Sharding and Partitioning

Replication scales reads. Sharding scales writes and total storage, by splitting data across multiple independent database nodes, each holding a subset of the data. It is a bigger commitment than replication: it is harder to undo, so reach for it only once a single node is genuinely the bottleneck.

8.1 Sharding Strategies

Strategy How It Works Weakness
Range-Based Split by value ranges (e.g. user IDs 1 to 1M on shard A) Hot-spotting: new users all land on the same shard if IDs are sequential
Hash-Based Hash the shard key, distribute evenly across shards Even distribution, but range queries ("all users created last week") now hit every shard
Directory-Based A lookup service maps keys to shards explicitly Flexible and rebalanceable, but the lookup service is a new critical dependency
Geographic Shard by region, keeping data close to its users Great for latency, complicated for users or data that cross regions

8.2 Choosing a Shard Key

The shard key determines everything. Pick badly and you get hot shards or queries that must fan out to every shard. The classic mistake: sharding a multi-tenant SaaS product by created_at, which sends all of today's traffic to one shard.

Quick Decision Rule: Do You Actually Need to Shard?

  1. Read-bound bottleneck? Add replicas or caching first. Do not shard.
  2. Single table too large for comfortable operations, but writes are fine? Consider partitioning within one database (not full sharding) first.
  3. Write throughput on one node is the actual proven bottleneck? Now sharding is justified.
  4. Multi-tenant product? Shard by tenant_id to keep each customer's data together.
Interview Tip. Say "I would shard by tenant_id rather than by row ID, so each customer's data stays on a single shard. That keeps their queries and transactions local instead of fanning out across the cluster." Naming the shard key choice, and why, is worth more than describing sharding in the abstract.
Extra Interview Tip: mention that sharding should be a last resort. Say "Before sharding, I would exhaust simpler options: better indexing, read replicas, caching, and vertical scaling. Sharding adds real operational complexity (rebalancing, cross-shard queries, and no more simple foreign keys across shards), so I would only reach for it once a single primary node genuinely cannot keep up with writes." This shows engineering maturity. Not reaching for the most complex tool first.

What Interviewers Usually Want to Hear

  • You treat sharding as a write-scaling and storage tool, distinct from replication
  • You know a bad shard key causes hot-spotting or cross-shard fan-out
  • You would exhaust simpler options (replicas, caching, indexing) before sharding
  • You know cross-shard joins and transactions are the real operational cost

Good default: shard only once write throughput genuinely bottlenecks a single node, pick a key that keeps related data together, and prefer hash-based distribution unless range queries are common.

Section 09

Caching Layers

Caching is usually the highest-leverage, lowest-risk way to improve database performance. It should be considered before sharding, and often before adding replicas.

9.1 Caching Strategies

Strategy How It Works Tradeoff
Cache-Aside App checks cache first; on miss, reads DB and populates the cache Simple, most common. First request after expiry is always slow.
Write-Through Every write goes to the cache and the DB together Cache always fresh, but every write pays the cache-write cost too
Write-Behind Write hits the cache immediately, DB write happens asynchronously Fastest writes, but risks data loss if the cache fails before flushing
Read-Through Cache itself is responsible for loading from the DB on a miss Simplifies app code, requires cache library or infra support

9.2 Cache Invalidation

Famously one of the two hard problems in computer science. The core question: when the underlying data changes, how does the cache find out?

TTL vs explicit invalidation 
# TTL-based: simplest, accepts some staleness
SET user:123 "{...}" EX 300     # expires automatically after 5 minutes

# Explicit invalidation on write: fresher, more moving parts
def update_user(id, data):
    db.update(id, data)
    cache.delete(f"user:{id}")   # next read repopulates from DB

Quick Decision Rule: Which Caching Strategy?

  1. Default, most read-heavy workloads? Cache-aside. Simple, predictable, easy to debug.
  2. Cache and DB must always be in sync? Write-through, at the cost of write latency.
  3. Write latency is critical and small loss is acceptable? Write-behind, with durability in mind.
  4. Want the cache library to handle the read path? Read-through, if your cache supports it.
Interview Tip. Say "I would use cache-aside with Redis in front of Postgres. Check cache, fall back to DB on miss, populate cache with a TTL. For anything that must be perfectly fresh, like a user's own balance right after they update it, I would invalidate explicitly on write instead of relying on TTL alone." Naming both TTL and explicit invalidation, and when each applies, shows real judgment.
Extra Interview Tip: name the thundering herd. If the interviewer says "what could go wrong with your cache," say "If a very hot key expires, I could get a thundering herd. Hundreds of requests all missing at once and slamming the database simultaneously. I would mitigate with a short-lived lock so only one request repopulates the cache while others wait briefly, or stagger TTLs with jitter to avoid synchronized expiry." This is the exact kind of "I have seen this break in production" answer that stands out.

What Interviewers Usually Want to Hear

  • You reach for caching before sharding. It is cheaper and reversible.
  • You know cache-aside as the default, and when write-through or write-behind fit instead
  • You name the thundering herd problem and a real mitigation
  • You choose TTL vs explicit invalidation based on how fresh the data must be

Good default: cache-aside with Redis, short TTLs plus explicit invalidation on write for anything user-visible immediately, and jittered expiry to avoid thundering herds.

Section 10

Common Mistakes and Performance Pitfalls

The database section of a system design interview is where candidates most often lose points on details they would normally catch in real code review, because they are talking instead of typing. This section is the direct list of what trips people up.

Symptom Likely Cause Fix
List endpoint gets slower as the table grows Offset pagination on a large table. The DB still scans and discards all skipped rows. Switch to cursor or keyset pagination on an indexed column
Simple query is unexpectedly slow Missing index, or a composite index with the wrong column order Run EXPLAIN ANALYZE, index the actual filter and sort columns
App makes hundreds of queries for one page load N+1 query problem: one query per row in a loop instead of a single batched query Use a JOIN, an IN (...) batch query, or a DataLoader-style batching layer
Two users' writes silently overwrite each other No optimistic locking. Last write wins with no conflict detection. Add a version column, reject writes with a stale version
Reports are slow and compete with production traffic Analytics queries running directly against the primary transactional database Route reporting to a read replica or a separate data warehouse
Storage keeps growing even after deleting old data Soft deletes, orphaned rows, or unpruned indexes and logs Scheduled cleanup jobs, table partitioning by date with old partitions dropped

Quick Decision Rule: The Performance Diagnosis Order

  1. Query slow? Run EXPLAIN ANALYZE first, before touching schema or code.
  2. Loop of queries in your app code? Batch them with a JOIN or an IN (...).
  3. List endpoint on a growing table? Cursor pagination on an indexed column.
  4. Reports competing with live traffic? Move them to a replica or a warehouse, not the primary.
Interview Tip. Build the habit of narrating scale as you design, not after being asked. Say "This endpoint will need an index on event_id and start_time together, and I will use cursor pagination since this table grows unbounded." Stating it proactively, even briefly, signals the habit interviewers are actually screening for.
Extra Interview Tip: the mistake that actually costs interview points. It is rarely picking the "wrong" database. It is forgetting to mention indexing, pagination, or the N+1 problem at all when designing a list endpoint. These are assumed baseline knowledge, and their absence reads as inexperience even if everything else in the answer is strong. Treat "how will this query perform at scale" as a question to answer for every endpoint you propose, not just the ones the interviewer explicitly asks about.

What Interviewers Usually Want to Hear

  • You proactively mention indexing and pagination without being prompted
  • You know the N+1 problem is not GraphQL-specific. It happens in any ORM.
  • You separate transactional and analytical workloads instead of running both on one database
  • You think about data growth and cleanup, not just the initial write path

Good default: narrate scale considerations as you design, not retroactively. Indexing, pagination, and query patterns are baseline, not bonus points.

Section 11

Interview Quick Reference

Time Allocation

Spend 5 to 8 minutes on the data model in a system design interview. It is usually the second major topic after the API surface. Cover schema, indexing, and one scaling decision, then move to the harder architectural tradeoffs.

What to Cover (in order)

  • State your database choice and why: "PostgreSQL, because the data is relational and needs transactions"
  • Sketch the core entities and relationships. 3 to 6 tables is enough.
  • Mention your primary indexes on the columns you will actually query
  • Name your consistency requirement: "Strong consistency on inventory, eventual is fine for the activity feed"
  • State your scaling plan in one sentence: replicas first, caching next, sharding only if truly needed

Signal Words and Your Response

If the interviewer says Your response
"Millions of users" or "at scale"Mention indexing, read replicas, and caching before jumping to sharding
"Strong consistency" or "must never be wrong"CP system, ACID transactions, pessimistic locking on hot rows
"Eventually consistent is fine"AP system, async replication, mention read-your-writes as the one exception users will notice
"Flexible schema" or "changes often"Document store, or JSONB column in Postgres for a hybrid approach
"Write-heavy" or "huge write volume"Wide-column store, or sharding by a key that distributes writes evenly
"Relationships are the core feature" (social, recommendations)Graph database, name a concrete traversal query as the reason

Quick Decision Rule: The 5-Minute Database Answer

  1. Database choice (30s): "Relational, PostgreSQL, because of transactional needs."
  2. Core schema (90s): Name 3 to 6 tables and their relationships out loud.
  3. Indexing (30s): "Composite index on (user_id, created_at) for the main list query."
  4. Consistency (30s): "Strong consistency on payments, eventual on the feed."
  5. Scale plan (30s): "Read replicas and caching first, sharding only if writes bottleneck a single node."
  6. Hand off (15s): "That covers the data layer. Want me to go deeper anywhere, or should I move to the API design?"
Interview Tip. Have one prepared sentence for every signal word above, the same way you would for API design. In the moment, you will not have time to derive the right answer from first principles. You will have time to remember a sentence you already trust. Practice saying each one out loud once before the interview, not just reading it.
Extra Interview Tip: hand off cleanly. End every database answer by explicitly inviting the next topic. Say "That covers the data layer. Want me to go deeper anywhere, or should I move to the API design?" Interviewers notice when candidates hand off cleanly. It shows you understand system design is a sequence of bounded discussions, not a single unstructured monologue.

What Interviewers Usually Want to Hear

  • You made a database decision without over-engineering
  • You named the tradeoff behind each choice, not just the choice itself
  • You proactively covered indexing and scale, not just the happy path
  • You moved on after 5 to 8 minutes instead of exhausting the topic

Good default: relational by default, index what you actually query, name your consistency requirement explicitly, scale with replicas and caching before sharding, then move on.
