Section 01

The Mental Model

Most people learn git commands before they learn what git actually is. That is why the commands feel arbitrary. Fix the mental model first, and the commands become obvious.

1.1 Three Trees, Not Two

Git tracks your project across three areas. Almost every command just moves data between them.

Area What It Holds Command That Moves Into It
Working Directory The actual files on disk, as you edit them you edit files directly
Staging Area (Index) A draft of the next commit git add
Repository (.git) Permanent, committed snapshots git commit

Once you see it this way, git add stops being "save my work" and becomes "stage this specific change for the next snapshot." That is why git add -p exists: you can stage half a file and leave the rest for later.

1.2 A Commit Is a Snapshot, Not a Diff

This is the single most-missed concept in interviews. Git does not store changes as a chain of diffs like older version control systems (SVN, CVS). Every commit is a full snapshot of the entire project at that point. Git only shows you diffs by comparing two snapshots. It does not store them that way.

Why it matters: this is why checking out an old commit is instant regardless of history length, why git bisect works, and why branches are so cheap.

1.3 A Branch Is Just a Pointer

A branch is a 41-byte text file containing a commit hash. That is it. It is not a copy of the codebase. HEAD is a pointer to whichever branch (or commit) you currently have checked out. This is why creating a branch is instant and why git can have thousands of branches in a large repo with no performance cost.

Quick Decision Rule: When to Commit, When to Stash

  1. Are the changes complete and meaningful? Stage and commit.
  2. Are you mid-experiment and might throw them away? Leave them in the working directory.
  3. Do you need to switch tasks right now? git stash, then pop later.
  4. Is the change to one file but only half the file is ready? Use git add -p to stage hunks.
Interview Tip. If asked "what is git," do not describe commands. Say "Git is a content-addressable snapshot system. Every commit is the full state of the project, branches are lightweight pointers to commits, and almost every operation is really just moving those pointers around." That answer signals you understand git, not just the CLI.
Extra Interview Tip: mention deduplication. Git deduplicates at the file level. If you commit 100 files and only one changes, the new commit's snapshot reuses the other 99 unchanged file objects rather than copying them. This is why repos do not balloon in size with every commit despite storing "full snapshots."

What Interviewers Usually Want to Hear

  • You know a commit is a snapshot, not a diff
  • You know a branch is a pointer, not a copy
  • You can name the three trees and what moves data between them
  • You understand why these design choices make git fast

Good default: think in snapshots and pointers, not files and folders. Every git command is manipulating one of the two.

Section 02

Branching

Branching is git's headline feature because it is nearly free. Use it liberally. A branch you never open a PR from costs nothing.

2.1 Core Commands

Branch management 
git branch feature/checkout-flow        # create a branch (does not switch to it)
git switch feature/checkout-flow        # switch to it (modern, git 2.23+)
git switch -c feature/checkout-flow     # create AND switch in one step
git checkout feature/checkout-flow      # older equivalent, still everywhere

git branch -d feature/checkout-flow     # delete, safe (refuses if unmerged)
git branch -D feature/checkout-flow     # delete, force (discards unmerged work)

git branch -a                            # list all branches, local + remote
git branch --merged                      # branches already merged into current

2.2 Branching Strategies

Strategy How It Works Best For
Trunk-Based Everyone commits small, frequent changes to main behind feature flags High-velocity teams, strong CI, continuous deployment
Feature Branching One branch per feature, merged via PR when done Most teams, default choice
Git Flow main, develop, release/*, hotfix/* with strict rules Scheduled releases, versioned software, multiple production versions live at once
Fork and PR Contributors fork the repo, no write access to origin Open source, external contributors

Quick Decision Rule: Which Branching Strategy?

  1. Small team, deploy multiple times a day? Trunk-based with feature flags.
  2. Normal team, PR review is the safety net? Feature branching, default choice.
  3. You ship versioned software with multiple supported releases? Git Flow.
  4. Open source project with external contributors? Fork and PR.
Interview Tip. Prefer switch and restore over checkout when explaining your workflow out loud. Say "I would use switch to move between branches and restore to discard file changes. Checkout does both, which is exactly the ambiguity that causes mistakes." This shows you know git evolved its own UX because the old commands were confusing even to experienced users.
Extra Interview Tip: name the trend, not just the choice. If an interviewer asks about branching strategy, mention that Git Flow is increasingly out of favor. Say "Git Flow made sense when releases were scheduled and infrequent. Most teams doing continuous deployment now use trunk-based development with feature flags instead, because long-lived branches are exactly what causes painful merges." That shows awareness of how team practices evolved, not textbook memorization.

What Interviewers Usually Want to Hear

  • You know branches are cheap and encourage using them often
  • You can name a branching strategy and its tradeoff, not just its name
  • You know the difference between local and remote branches
  • You clean up merged branches instead of letting them pile up

Good default: short-lived feature branches, one per unit of work, merged via PR, deleted immediately after merge.

Section 03

Merge vs Rebase

This is the single most common git interview question, and the one people most often answer with vibes instead of understanding. Both integrate changes from one branch into another. They produce different history shapes.

Same two commits, two different resulting histories.

3.1 The Core Tradeoff

Aspect Merge Rebase
History shape Preserves exact history, branch points visible Linear, rewritten history, looks like it happened in order
Safety Never rewrites existing commits Rewrites commit hashes, dangerous on shared branches
Traceability You can see exactly when and how branches integrated You lose the record that a branch ever diverged
Conflict resolution Resolve once, in a single merge commit May need to resolve the same conflict repeatedly, once per replayed commit
Merge and rebase 
git merge feature/checkout-flow      # merge feature into current branch

git checkout feature/checkout-flow
git rebase main                       # replay feature's commits on top of main

git rebase -i HEAD~4                  # interactive rebase: squash, reword, reorder
Interview Tip. Do not declare a universal winner. Say "I use rebase to clean up my own commits before they are shared, and merge to integrate finished work into main. The rule that matters is: never rebase history other people already have." That single sentence answers the question interviewers are actually asking: do you understand the danger, not just the syntax.
Extra Interview Tip: mention git pull --rebase. A plain git pull creates a merge commit every time your local branch has diverged from origin, which clutters history on active branches. Configuring pull.rebase=true replays your local commits on top instead, keeping history linear without changing team workflow. This is a real setting senior engineers configure and juniors usually do not know exists.

Quick Decision Rule: Merge or Rebase?

  1. Integrating a finished feature branch into main? Merge. Keep the record.
  2. Cleaning up your own local commits before opening a PR? Interactive rebase.
  3. Updating your feature branch with the latest main, before others have pulled it? Rebase, for a clean linear history.
  4. Has anyone else already pulled this branch? If yes, never rebase it. Merge instead.

What Interviewers Usually Want to Hear

  • You know rebase rewrites history and merge does not
  • You know the exact rule for when rebase becomes dangerous
  • You can justify a choice instead of stating a preference
  • You know interactive rebase is a cleanup tool, not just an integration tool

Good default: rebase locally to keep your own commits clean, merge to integrate into shared branches, never rebase what others have already pulled.

Section 04

Resolving Conflicts

A conflict means git found two changes to the same lines and cannot guess which one you want. It is not a failure state. It is git correctly asking a question it cannot answer on its own.

4.1 Reading Conflict Markers

Conflict marker anatomy 
<<<<<<< HEAD
const TAX_RATE = 0.08;              // your current branch's version
=======
const TAX_RATE = getRegionalTax();  // the incoming branch's version
>>>>>>> feature/dynamic-tax

Everything between <<<<<<< HEAD and ======= is your current branch. Everything between ======= and >>>>>>> is the branch being merged in. Delete the markers, keep whichever code (or a combination) is correct, then stage and continue.

After resolving 
# after manually resolving the file:
git add checkout.js
git commit                    # if you were merging
git rebase --continue         # if you were rebasing

# bail out entirely and go back to before the conflict:
git merge --abort
git rebase --abort

Quick Decision Rule: How to Resolve

  1. Both changes are needed and do not overlap logically? Keep both, remove markers.
  2. Unsure which side is correct? Check git log on both commits, or ask the author. Do not guess.
  3. Conflict is in a lockfile (package-lock.json, yarn.lock)? Delete and regenerate, do not hand-merge.
  4. In over your head mid-rebase? git rebase --abort and try merge instead. No shame in it.
Interview Tip. If asked to resolve a conflict live, narrate your process: "I am reading both sides of the marker to understand intent, not just picking one blindly. I want to know why each side changed this line before deciding whether to keep one, the other, or merge both." Interviewers are watching whether you understand the conflicting code, not whether you can delete <<<<<<< symbols fast.
Extra Interview Tip: mention git rerere. "Reuse recorded resolution" lets you record how you resolved a conflict so the same fix is auto-applied next time. If you are rebasing a long-lived branch and hitting the same conflict on every replayed commit, enable rerere and git remembers how you resolved it the first time. Almost nobody outside senior engineers who have suffered through painful rebases knows this exists.

What Interviewers Usually Want to Hear

  • You can read conflict markers correctly without confusing which side is which
  • You resolve based on understanding intent, not by picking randomly
  • You know how to safely bail out with --abort
  • You know lockfile conflicts should be regenerated, not hand-edited

Good default: read both sides before touching anything, resolve for correctness not speed, and know that --abort is always a safe escape hatch.

Section 05

Undoing Things

This is where interview anxiety spikes hardest, because the commands sound similar and the wrong one can genuinely lose work. Learn them by what tree they touch, not by memorizing flags.

5.1 The Undo Ladder

Command What It Undoes Rewrites Shared History?
git restore <file> Uncommitted changes in working directory No
git restore --staged <file> Unstages a file, keeps the edits No
git reset --soft HEAD~1 Undoes last commit, keeps changes staged Yes, local only
git reset --mixed HEAD~1 Undoes last commit, unstages changes (default mode) Yes, local only
git reset --hard HEAD~1 Undoes last commit AND discards all changes Yes, destructive
git revert <commit> Creates a new commit that undoes an old one No, safe on shared branches

5.2 The Safety Net: Reflog

Most people do not know this exists, which is exactly why panicking over a "lost" commit is usually unnecessary. Git keeps a log of every place HEAD has pointed, even after resets, rebases, and branch deletions.

Reflog rescue 
git reflog                     # shows every HEAD movement, newest first
# a1b2c3d HEAD@{0}: reset: moving to HEAD~1
# f9e8d7c HEAD@{1}: commit: add checkout validation   <- the "lost" commit

git checkout f9e8d7c            # recover it directly
git branch recovered-work f9e8d7c   # or save it to a new branch

Quick Decision Rule: Which Undo?

  1. Haven't committed yet, just want to discard edits? git restore.
  2. Committed locally, nobody has pulled it, want it gone? git reset.
  3. Already pushed, others may have pulled it? git revert, never reset.
  4. Think you lost a commit entirely? git reflog before you panic.
Interview Tip. If asked "how would you recover a commit you accidentally deleted," do not say "you can't." Say "Almost nothing in git is truly gone immediately. The reflog tracks every place HEAD has pointed for about 90 days by default, so I would find the commit hash there and check it back out." This is one of the highest-signal answers in the whole topic because it shows you have actually recovered from a real mistake before.
Extra Interview Tip: distinguish git rm, .gitignore, and git rm --cached. If a file was committed by accident and you want it out of git but still on disk, say a .env file, you would use git rm --cached, then add it to .gitignore. Plain git rm deletes it from disk too, which usually is not what people actually want. This exact scenario, accidentally committing secrets, comes up constantly in real teams.

What Interviewers Usually Want to Hear

  • You know reset is for local/unshared history, revert is for shared history
  • You know the reflog exists and treat it as a real safety net, not trivia
  • You can explain the difference between soft, mixed, and hard reset
  • You know how to remove a committed secret from tracking without deleting it locally

Good default: revert on shared history, reset only on your own unpushed commits, and reflog before assuming anything is unrecoverable.

Section 06

Git Internals

You do not need this for day-to-day work, but a little internals knowledge is the fastest way to sound senior in an interview. It shows you did not just memorize commands.

6.1 The Object Model

Object What It Stores
BlobThe raw content of a single file, nothing else: no filename, no metadata
TreeA directory listing: filenames mapped to blob or tree hashes
CommitA pointer to one tree (the snapshot), plus parent commit(s), author, message, timestamp
TagA named, permanent pointer to a specific commit, usually for releases

Every object is identified by the SHA-1 (or SHA-256 in newer repos) hash of its own content. This is why git is called "content-addressable." The ID is a hash of what is inside.

Inspecting the object model 
git cat-file -p HEAD              # inspect the commit object: tree, parent, author, message
git cat-file -p HEAD^{tree}       # inspect the tree: filenames and blob hashes
git hash-object -w somefile.txt   # manually create a blob, prints its SHA

6.2 HEAD, Detached HEAD, and Why It Trips People Up

HEAD normally points to a branch, which points to a commit. If you check out a commit hash directly instead of a branch name, HEAD points straight at that commit. This is "detached HEAD." Any new commits you make there are not attached to a branch, so they can become unreachable (and eventually garbage collected) the moment you switch away, unless you create a branch to hold them first.

Detached HEAD rescue 
git checkout a1b2c3d          # detached HEAD, you are floating, not on a branch
git switch -c rescue-branch    # attach your new work to a real branch immediately

Quick Decision Rule: How to Escape Each Git State

  1. On a branch, want a quick look at an old commit? Check it out, then git switch - to return.
  2. On detached HEAD with new commits you want to keep? git switch -c rescue-branch immediately.
  3. On a branch with uncommitted changes you want to set aside? git stash.
  4. On a branch with uncommitted changes blocking checkout? git stash first, switch, then git stash pop.
Interview Tip. If asked why git hashes objects by content, say "It means git can detect corruption instantly. If a byte changes, the hash no longer matches. It also means identical content is stored once, even across different files or commits, which is why git repos compress so well despite storing full snapshots." That is the actual engineering reason, not just a fun fact.
Extra Interview Tip: detached HEAD is a feature, not a bug. Say "Detached HEAD is how you explore history safely. If you decide your exploration is worth keeping, switch -c to attach it to a real branch. If you do not, just switch back and the commits get garbage collected." That framing shows you understand git is not fragile, it just requires intentional state management.

What Interviewers Usually Want to Hear

  • You can name the four object types and what each one holds
  • You understand content-addressing and why it is useful, not just what it is called
  • You know what detached HEAD means and how to escape it safely
  • You treat internals as something you understand, not memorized trivia

Good default: commits point to trees, trees point to blobs and other trees, everything is addressed by the hash of its content.

Section 07

Remotes and GitHub

Git is distributed version control. GitHub is a hosted remote plus a collaboration layer on top (PRs, issues, actions). Keep the two mentally separate. Everything in this section except the PR workflow is plain git, not GitHub-specific.

7.1 Fetch vs Pull vs Push

Command What It Does
git fetchDownloads new commits from the remote, does NOT touch your working files or branches
git pullfetch + merge (or rebase if configured) into your current branch, in one step
git pushUploads your local commits to the remote branch
git push --force-with-leaseForce-push that fails safely if someone else pushed in the meantime, see below

7.2 Fork vs Branch

A branch lives inside one repository. A fork is an entirely separate copy of the whole repository, under your own account, used when you do not have write access to the original. Open source contributors fork, then branch inside their fork, then open a PR from their fork's branch back to the original repo.

Quick Decision Rule: Fetch or Pull?

  1. Just want to see what is on the remote? git fetch, inspect, then decide.
  2. Confident the remote will merge cleanly into your branch? git pull (configured to rebase if you prefer linear).
  3. About to start work and want a clean base? Fetch first, then rebase or merge as needed.
  4. On a long-running shared branch, want minimal surprise? Fetch and review before pulling.
Interview Tip. If asked to describe a typical GitHub workflow end to end, keep it tight: "Branch off main, commit locally, push to origin, open a PR, address review comments, squash or merge once approved, delete the branch, and let CI gate the merge." A clean six-step answer signals real experience more than a long explanation of any single step.
Extra Interview Tip: name the force-with-lease flag. After any rebase on a shared branch, use --force-with-lease, never plain --force. Plain force overwrites the remote branch no matter what, even if a teammate pushed commits you do not have. --force-with-lease checks first that the remote has not changed since you last fetched, and refuses if it has. This single flag prevents one of the most common ways teams lose each other's work.

What Interviewers Usually Want to Hear

  • You know fetch downloads without merging, and pull does both
  • You use --force-with-lease instead of --force on shared branches
  • You can distinguish a fork (separate repo) from a branch (inside one repo)
  • You can describe a full PR lifecycle without rambling

Good default: fetch before you assume, pull with rebase configured, and never force-push without --force-with-lease.

Section 08

Code Review and PR Etiquette

This is the part most git guides skip, but it is frequently what behavioral-style git questions are actually probing. "Tell me how you handle a disagreement in code review" is a git-adjacent question in disguise.

8.1 Writing a PR People Actually Want to Review

  • Keep it small. A 2000-line PR gets a rubber-stamp approval, not a real review.
  • Write a description that explains why, not just what changed (the diff already shows what).
  • Self-review your own diff before requesting review. You will catch half your own mistakes.
  • Link the ticket or issue so reviewers have context without asking.

8.2 Commit Message Discipline

Commit message discipline 
# weak:
git commit -m "fix bug"
git commit -m "wip"
git commit -m "more changes"

# strong. Imperative mood, explains why:
git commit -m "Fix race condition in checkout by locking inventory row on read

Without the lock, two concurrent checkouts could both read stock=1
and both succeed, overselling the last unit."

Quick Decision Rule: Squash Merge or Merge Commit?

  1. Default for a feature branch into main? Squash merge. One clean commit per feature.
  2. Want to preserve individual commit history from the branch? Merge commit, not squash.
  3. Hotfix or trivial one-liner? Squash for a clean main history.
  4. Open source contribution where the project keeps author attribution? Merge commit, retain the original commits.
Interview Tip. Mention squash merging. Say "I usually squash-merge feature branches into main so the history reads as one clean commit per feature, and I keep my messy WIP commits during development. They are useful to me, not to the permanent record." This shows you separate "history for me while working" from "history for the team forever," which is a distinction juniors rarely make.
Extra Interview Tip: review disagreement is a behavioral question in disguise. If asked how you would respond to disagreement in review, say "I would ask the reviewer to explain the concern with a concrete example rather than debating in the abstract, and I default to trusting their read on code they maintain more than mine, unless I have data that says otherwise." This answers the actual question, collaboration maturity, using git and PR language.

What Interviewers Usually Want to Hear

  • You keep PRs small and reviewable, not "everything I did this sprint"
  • You write commit messages that explain why, not just what
  • You self-review before asking others to review
  • You handle review disagreement with curiosity, not defensiveness

Good default: small PRs, imperative commit messages that explain intent, self-review first, squash-merge into a clean main history.

Section 09

Debugging with Git

Git is also a debugging tool, not just a history tool. This section is where you separate yourself from candidates who only know it as "the thing that stores my code."

9.1 git bisect: Binary Search for the Bad Commit

When a bug appeared somewhere in the last 200 commits and you do not know which one, do not check them one by one. Bisect does a binary search: you mark one commit good, one bad, and git checks out the midpoint for you to test, repeating until it isolates the exact commit.

git bisect workflow 
git bisect start
git bisect bad                      # current commit has the bug
git bisect good v1.4.0              # this old tag was fine
# git checks out the midpoint automatically. You test it, then:
git bisect good                     # or: git bisect bad
# ...repeats, narrowing the range each time, ~log2(n) steps total
git bisect reset                    # done, return to where you started

For 500 commits, that is about 9 tests to find the exact culprit, instead of up to 500.

9.2 git blame and git log: Who, When, Why

History forensics 
git blame checkout.js -L 40,60      # who last touched each of these lines, and when
git log -p --follow checkout.js     # full history of a file, including across renames
git log -S "TAX_RATE"               # find commits that added/removed this exact string
git log --oneline --graph --all     # visualize branch structure in the terminal

Quick Decision Rule: Which Debugging Tool?

  1. Know the bad commit is somewhere in the last N commits? git bisect.
  2. Need to know who wrote a specific line and why? git blame, then read the linked PR or ticket.
  3. Need to find when a specific string was added or removed? git log -S "string" (the pickaxe).
  4. Need a visual map of branch structure? git log --oneline --graph --all.
Interview Tip. Mention automating bisect: git bisect run ./test.sh lets git run a script at each step and read the exit code, fully automating the search with zero manual testing. Say "If I have a reliable failing test, I would script it and let bisect run unattended rather than testing each commit by hand." That single line separates "I have heard of bisect" from "I have actually used it under pressure."
Extra Interview Tip: do not describe blame as "who to yell at." Say "I use blame to find the commit and PR that introduced a line, so I can read the original context, the linked ticket, and the reasoning. Not to assign fault." Interviewers notice when candidates frame git tools around understanding versus around blame culture.

What Interviewers Usually Want to Hear

  • You know bisect does binary search, and roughly why that is fast
  • You know bisect can be automated with a test script
  • You use blame and log to recover context, not to assign fault
  • You know -S (pickaxe) can search history by code content, not just messages

Good default: reach for bisect before manually checking out commits, and treat git history as a debugging tool with context, not just a backup.

Section 10

Common Mistakes and Recovery

The fastest way to look senior in a git interview is not reciting commands. It is staying calm when the scenario is "I broke something." This section is a direct answer to the anxiety this whole topic causes: here is exactly what to do for the mistakes everyone makes.

"I just..." Fix
Committed to the wrong branchgit reset --soft HEAD~1, switch to the right branch, git stash pop or re-commit
Need to edit my last commit messagegit commit --amend (only if not yet pushed, or you are prepared to force-push)
Committed a secret or .env fileRotate the secret immediately, then git rm --cached + .gitignore. If already pushed, the secret is compromised; rotating it matters more than scrubbing history
Want to save half-finished work to switch tasksgit stash, later git stash pop
Deleted a branch by mistakegit reflog, find the last commit on that branch, git branch <name> <hash>
Have merge conflicts I do not understandgit merge --abort, take a breath, re-read both sides slower, or ask the other author
Force-pushed and broke a teammate's branchThey run git fetch then git reset --hard origin/branch to resync. Communicate first.
Am on detached HEAD with new commitsgit switch -c rescue-branch immediately, before doing anything else

Quick Decision Rule: The 30-Second Recovery

  1. First move on any git disaster? Run git status and git reflog. Do not touch anything yet.
  2. Want to back out of a merge or rebase cleanly? git merge --abort or git rebase --abort.
  3. Lost a commit, branch, or ref? Look in reflog before assuming it is gone.
  4. Committed a secret? Rotate the credential. Then scrub tracking. Rotation first, history second.
Interview Tip. If given a live "fix this repo" scenario, narrate as you go: "Let me check git status and git log first to understand the current state before I run anything that changes it." Interviewers are often more interested in your diagnostic order than your typing speed.
Extra Interview Tip: name the mistake that actually fails interviews. It is rarely the git error itself. It is candidates who freeze or say "I would just delete the repo and re-clone." That answer signals panic, not skill, and it destroys uncommitted work. The strongest answer to almost any "I broke git" scenario starts with "First, I would check git reflog and git status before touching anything, because in git almost nothing is actually gone." Say that sentence out loud before diagnosing the specific problem. It buys you thinking time and it is true.

What Interviewers Usually Want to Hear

  • You diagnose with status, log, reflog before running destructive commands
  • You know rotating a leaked secret matters more than scrubbing git history
  • You stay calm and methodical instead of proposing to nuke and re-clone
  • You communicate with teammates before force-pushing to a shared branch

Good default: diagnose before you act, assume recovery is possible until proven otherwise, and treat "I do not know, let me check" as a legitimate first move.

Section 11

Interview Quick Reference

Time Allocation

Git questions are rarely the main event. They show up as warm-ups, live-coding hiccups, or one behavioral question about collaboration. Answer cleanly in under a minute and let the interviewer move on. Over-explaining git signals nerves more than depth.

Signal Words and Your Response

If the interviewer says Your response
"Walk me through your git workflow"Branch, commit, push, PR, review, squash-merge, delete branch. Six steps, said fast.
"Merge or rebase, and why"Rebase locally before sharing, merge to integrate. Never rebase what others have pulled.
"How would you find which commit broke this"git bisect, automate with bisect run if there is a reliable test
"You accidentally committed something sensitive"Rotate the credential first, scrub tracking second
"How do you handle a disagreement in review"Ask for a concrete example, default to trusting the maintainer, use data to push back
"Tell me about a time you broke something"Have one real story ready: what broke, how you found it (bisect, reflog, blame), how you fixed it

Quick Decision Rule: The 60-Second Git Answer

  1. State the mental model if relevant (10s): "Commits are snapshots, branches are pointers."
  2. Name your default workflow (15s): "Short feature branches, PRs, squash-merge."
  3. Name the one safety rule that applies (15s): "Never rebase shared history." or "Revert, do not reset, once it is pushed."
  4. If it is a "something broke" question, lead with diagnosis (10s): "I would check reflog before assuming anything is lost."
  5. Stop talking (10s): Let the interviewer ask a follow-up rather than filling the silence.
Interview Tip. You answer git questions fast and move on, not a five-minute git lecture. Have one real "I broke git and fixed it" story memorized before the interview. It does not need to be dramatic: an accidental force-push, a bad rebase, a committed secret. What matters is that you can narrate the diagnosis (what you checked first) and the fix (what command, why that one) in under 90 seconds. This single prepared story covers most behavioral-flavored git questions at once.
Extra Interview Tip: have the recovery story arc ready. The story does not need to be dramatic. It just needs three beats: what broke, what you checked first (the diagnosis), and what command fixed it plus why that one. Candidates who can name the order of operations under pressure sound senior. Candidates who say "I would just re-clone" do not.

What Interviewers Usually Want to Hear

  • You answer git questions fast and move on, not a five-minute git lecture
  • You have one real recovery story ready, not just command syntax
  • You default to the safe option (revert, --force-with-lease) without being asked
  • You frame git as a tool for understanding history, not assigning blame

Good default: snapshots and pointers, short branches, rebase-then-merge on your own work, revert on shared work, reflog before panic, one real story ready to tell.
