Model routing

GPT-6 Astra

Astra is the model I would reach for when the job needs visual judgment, active verification, or aggressive bug hunting. Sol is still the daily workhorse.

Do not read this as “one model replaced everyone.” Read it as a routing guide: use the expensive model when it can close the loop itself, then stay boring when the task is already clear.

01

My current model split

Astra

frontend QA, bug hunts, tool-heavy agents

Best when the model needs to build, run, inspect, click, compare, and correct. This is where the launch data shows the clearest jump.

Sol

daily coding, routine implementation

My default for ordinary repo work where I am not seeing enough extra value from Astra to justify burning allowance faster.

Fable 5.1

long-horizon planning, architecture reviews

I still like it for long planning sessions where the model needs to hold the whole architecture in its head. Workflow preference, not a universal benchmark win.

The pricing caveat from my reel. My “8x subscription money” line refers to the subscription setup I personally compared. It is not API token pricing.

02

The benchmark story is weird

Astra looks dramatically better on some agentic tasks, and only slightly better on some coding tasks. That difference matters more than the headline.

57.9%Terminal-Bench 4.0, Astra vs 37.3% Sol and 55.8% Fable 5.1.
74.1%DeepSWE v1.1, Astra vs 72.7% Sol. Only +1.4 points.
95.9%BenchCAD, Astra vs 83.3% Sol and 84.3% Fable 5.1.
72.6%OSWorld 2.0, Astra vs 65.7% Sol, with less simulated task time reported.

My read: the bigger jump is not “writes code better in every situation.” It is “acts better while using tools, screens, terminals, and verification loops.”

Benchmark numbers here come from the source links in the receipts section. Vendor benchmarks are useful signals, not a substitute for your own repo-level eval.

New CLIs, GUIs, and workflows where the model has to infer how the environment works.

06

Science + code workflows

Simulations, data analysis, fitting models, and checking whether implementation matches a stated method.

Cherry on top: use the expensive model where it can close the loop itself. If you manually check every step, you may be paying frontier prices for autocomplete with nicer manners.

04

Where I would not default to it

Small feature in a familiar repoUse Sol. Low novelty, easy to verify.
Routine refactorUse Sol, especially when requirements and tests are clear.
Boilerplate or CRUDUse Sol. Frontier reasoning is usually wasted here.
Visual frontend from scratchUse Astra. Visual judgment and browser verification matter.
Hard bug with unclear root causeUse Astra. Make it reproduce, inspect logs, form hypotheses, and verify the fix.
Architecture plan across many systemsUse Fable or Astra, depending on whether execution follows immediately.

OpenAI says Astra can use Work/Codex allowance faster than Sol. Route by expected value: will the extra capability change the outcome, or just make the same task more expensive?

05

3 prompts that make Astra earn it

Visual frontend build
Build this inside the existing app, not as a disconnected demo.
Preserve the current architecture and component conventions.
Run the app, inspect it in the browser, compare against the reference, and iterate until the visual differences are small.
Do not rewrite unrelated code.
Before finishing, verify responsive behavior, loading/error states, keyboard interaction, and console errors.
Bug hunt, not refactor cosplay
Investigate this as a bug, not a refactor request.
First reproduce the failure.
Then trace the symptom through state, network calls, logs, and relevant code paths.
Maintain a short list of hypotheses and eliminate them with evidence.
Do not patch until you can explain the root cause.
After the minimal fix, add or update the test that would have caught it and rerun the relevant suite.
Paper vs implementation audit
Audit the paper against the implementation.
For every methodological claim that affects results, find the corresponding code, config, constant, dataset, or runtime parameter.
Return a table: CLAIM | IMPLEMENTATION EVIDENCE | MATCH / MISMATCH | SEVERITY | CONFIDENCE.
Do not assume the paper is correct. Do not infer missing implementation details.
Flag anything that could materially change the reported result.

06

Cost, context, and benchmark caveats

1.05MAstra context window. Max output is listed as 128K.
$10 / $50Astra API input and output per 1M tokens in the referenced model page.

ARC Prize reports Astra at 62.7% on its Standard harness and 99.9% with OpenAI’s Provider Adapter harness. Both matter, but they are not interchangeable numbers.

Astra is also reported at a Critical cybersecurity capability level. Treat that as a capability and safety note, not permission for offensive work.

My rule: benchmark the workflow, not the screenshot. Same task, same repo, same tool access, same acceptance criteria, then record time-to-correct-solution plus tokens or credits consumed.
