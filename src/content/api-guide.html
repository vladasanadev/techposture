Section 01

Choosing the Right Protocol

Default to REST unless the requirements give you a clear reason not to.

In a system design interview, the goal is not to pick the most sophisticated protocol. It is to choose the simplest option that satisfies the requirements, explain why, and keep moving.

Protocol Best For Signals to Listen For Avoid When
REST Web/mobile apps, CRUD, public APIs Standard request/response, resources, simple integrations Rarely a bad default
GraphQL Flexible client-driven data fetching Different clients need different fields, over-fetching, under-fetching Simple CRUD where endpoints are predictable
gRPC / RPC Internal service-to-service communication Microservices, low latency, high throughput, strongly typed contracts Public browser-facing APIs unless paired with a gateway or proxy
WebSocket Two-way real-time communication Chat, multiplayer, collaborative editing, live trading Normal request/response flows
SSE One-way server-to-client streaming Notifications, live dashboards, progress updates, event feeds Client needs frequent two-way communication

Quick Decision Rule

Ask these questions in order:

  1. Is normal request/response enough? Use REST.
  2. Do different clients need very different data shapes? Consider GraphQL.
  3. Is this mostly internal service-to-service communication where performance matters? Consider gRPC.
  4. Do both client and server need to send messages at any time? Use WebSocket.
  5. Does only the server need to continuously push updates? Consider SSE.
Interview Tip. Do not spend five minutes comparing protocols unless protocol choice is actually central to the problem. A strong answer sounds like: "I will use REST for the main client-server API because the access patterns are straightforward CRUD. If we later need real-time updates, I would add WebSockets for that specific path." This shows that you can make a decision now without over-engineering, while still leaving room for the architecture to evolve.
Extra Interview Tip: state the requirement before the technology. Instead of saying "I want to use WebSockets", say "Users need to receive updates within seconds without polling, so I would use a persistent WebSocket connection." The second version is stronger because the technology follows from the requirement.

What Interviewers Usually Want to Hear

They are usually testing whether you can:

  • Identify the communication pattern
  • Choose a reasonable default
  • Explain one meaningful tradeoff
  • Avoid unnecessary complexity

You do not need to prove that one protocol is universally better.

Good default: REST first, specialize only where the requirements justify it.

Section 02

REST, the Default Choice

2.1 Resource Modeling

Think about the things in your system, not the actions. Resources should be plural nouns. Map your core entities directly to URL paths.

Rules:

  • Use plural nouns: /events, /bookings, /users (never /getEvent or /createUser)
  • Nest resources when the parent is required: /events/{id}/tickets
  • Use query parameters for optional filters: /tickets?event_id=123&section=VIP
  • Keep nesting shallow, avoid going deeper than 2 levels
Core entity examples (Ticketmaster-style) 
GET    /events                     # List all events
GET    /events/{id}               # Get one event
POST   /events                     # Create new event
PUT    /events/{id}               # Replace entire event
PATCH  /events/{id}               # Update partial fields
DELETE /events/{id}               # Remove event

# Relationships
GET    /events/{id}/tickets        # Tickets for this event (parent required)
POST   /events/{id}/bookings       # Create a booking for this event
GET    /tickets?event_id=123       # Optional filter (flat resource)
GET    /events?city=NYC&page=2     # Filter and pagination

2.2 HTTP Methods

Each method has a clear purpose. The most important concept is idempotency: calling the same request multiple times produces the same result.

Method Purpose Idempotent?
GET Retrieve resources. Never changes state. Yes
POST Create a new resource. Server assigns the ID. No
PUT Replace entire resource. Creates if missing. Yes
PATCH Update partial fields only. Maybe
DELETE Remove resource. Repeat equals same end state (404). Yes

Why idempotency matters: networks fail and clients retry requests. GET, PUT, DELETE are safe to retry. POST is not, two POST calls create two bookings.

2.3 Passing Data to APIs

There are three places to put data in a request. Choosing correctly makes your API intuitive.

Location Format Use When
Path parameter /events/123 Required, identifies the specific resource
Query parameter ?city=NYC&page=2 Optional, filtering, sorting, pagination
Request body JSON object Creating or updating, complex or sensitive data
Combined example 
POST /events/123/bookings?notify=true
{
  "tickets": [{"section": "VIP", "quantity": 2}],
  "payment_method": "credit_card"
}

# Path param:   123         (which event, required)
# Query param:  notify=true (optional behavior)
# Body:         tickets, payment (the actual data)

2.4 HTTP Status Codes

You only need to know the common ones. The most important distinction is 4xx (client error) vs 5xx (server error).

Code Name When to Use
200OKStandard success for GET, PUT, PATCH
201CreatedPOST succeeded, new resource was made
204No ContentSuccess but no body to return (DELETE, some PATCH)
400Bad RequestMalformed syntax, missing required fields
401UnauthorizedNo auth credentials provided (needs to log in)
403ForbiddenAuth is valid, but no permission for this action
404Not FoundResource does not exist
409ConflictState conflict, duplicate booking, optimistic lock
422Unprocessable EntityRequest is well-formed but fails validation
429Too Many RequestsRate limit exceeded, retry after delay
500Internal Server ErrorBug or crash on the server side
503Service UnavailableServer is down or overloaded

Quick Decision Rule: Picking the Right Method

Match the method to the intent, not the action.

  1. Reading data without changing anything? Use GET.
  2. Creating a new resource where the server picks the ID? Use POST.
  3. Replacing a resource with a new full version? Use PUT.
  4. Updating a few fields without sending the whole object? Use PATCH.
  5. Removing a resource and being okay with repeat calls? Use DELETE.
Interview Tip. When asked to design a CRUD endpoint, do not just list the five methods. Say "I would use POST for create, GET for read, PATCH for partial update, and DELETE for remove. I would skip PUT because PATCH is more efficient for partial updates in this system." That sentence shows you understand why the methods exist, not just what they are called.
Extra Interview Tip: idempotency is not trivia. If an interviewer asks why POST is not idempotent, the answer is: "Two POSTs create two resources, so the state changes with each call. PUT and DELETE can be repeated safely because the end state is the same. This matters for retry logic, payment flows, and any system where the network might drop mid-request." That answer ties the concept to production reality.

What Interviewers Usually Want to Hear

  • You modeled the system as resources, not actions
  • You explained when to nest vs when to use query parameters
  • You understood why idempotency matters for retries and payments
  • You chose status codes based on the situation, not from memory

Good default: plural nouns, GET for reads, POST for create, PATCH for partial update, 2xx for success, 4xx for client error, 5xx for server error.

Section 03

GraphQL

3.1 What Problem It Solves

REST endpoints return a fixed shape. A mobile app may only need event name and date, while the web dashboard needs full details with venue and ticket data. With REST you either:

  • Create multiple endpoints for different use cases (endpoint proliferation)
  • Return everything and make clients filter (over-fetching, wastes bandwidth)

GraphQL uses a single endpoint that accepts queries describing exactly what data the client wants. The server returns precisely that shape, nothing more.

3.2 Schema Design

You define types and their relationships once. Clients can traverse the graph in a single query.

GraphQL schema example 
type Event {
  id:      ID!
  name:    String!
  date:    DateTime!
  venue:   Venue!         # Nested type, traversable
  tickets: [Ticket!]!     # List of tickets
}

type Venue {
  id:      ID!
  name:    String!
  address: String!
}

type Query {
  event(id: ID!): Event
  events(limit: Int, after: String): [Event!]!   # Cursor pagination
}

type Mutation {
  createBooking(input: BookingInput!): Booking!
  cancelBooking(id: ID!): Boolean!
}

type Subscription {
  ticketSold(eventId: ID!): TicketEvent!          # Real-time updates
}

3.3 Query Examples

The same endpoint handles all queries. Each client requests exactly what it needs.

Mobile vs web queries 
# Mobile: only name and date
query GetEventMobile {
  event(id: "123") {
    name
    date
  }
}

# Web: full details in one round trip
query GetEventWeb {
  event(id: "123") {
    name
    date
    venue { name address }
    tickets { section price available }
  }
}

# Mutation
mutation CreateBooking {
  createBooking(input: { eventId: "123", tickets: [{section: "VIP", qty: 2}] }) {
    id
    status
  }
}

3.4 The N+1 Problem (Most Important GraphQL Gotcha)

When you query 100 events with their venues, a naive implementation fires 101 database queries: 1 for events, then 1 per event for its venue. This destroys performance at scale.

N+1 problem and the fix 
# Problem: 100 events = 101 queries
# 1 query:  SELECT * FROM events LIMIT 100
# 100 more: SELECT * FROM venues WHERE id = ? (once per event)

# Solution: DataLoader batches related queries
class VenueLoader(DataLoader):
    async def batch_load_fn(self, venue_ids):
        # 1 query: SELECT * FROM venues WHERE id IN (...all ids...)
        venues = await db.query('SELECT * FROM venues WHERE id = ANY($1)', [venue_ids])
        return [venues_by_id.get(id) for id in venue_ids]

3.5 When to Use GraphQL

Situation Use GraphQL?
Mobile app needs different data than web dashboardYes, classic use case
Frontend team iterates without backend involvementYes, they request new fields freely
Interviewer says over-fetching or under-fetchingYes, direct signal
Simple CRUD app with uniform clientsNo, REST is simpler
You need simple HTTP caching (CDN, browser cache)No, REST GET is cacheable, GraphQL POST is not
Public API for third-party developersNo, REST is more familiar and documented

Quick Decision Rule: REST or GraphQL?

  1. One client type, uniform data needs? Use REST.
  2. Multiple client types needing different shapes? Use GraphQL.
  3. Frontend team shipping faster than backend can ship? Use GraphQL.
  4. Public API for unknown third-party developers? Use REST.
  5. You need CDN-level caching? Use REST.
Interview Tip. When you mention GraphQL in an interview, always mention its cost. Say "GraphQL solves over-fetching but introduces N+1 query risk and breaks HTTP caching. For this system, I would default to REST and only reach for GraphQL if mobile and web clients need very different data shapes." This signals you understand tradeoffs, not just features.
Extra Interview Tip: name the N+1 problem out loud. If you say "I would use DataLoader to batch queries" without being asked, you immediately signal senior-level thinking. It shows you have shipped GraphQL at scale and know where it breaks.

What Interviewers Usually Want to Hear

  • You know GraphQL solves over-fetching and under-fetching
  • You understand the N+1 problem and how to mitigate it
  • You can articulate when GraphQL is the wrong choice
  • You understand GraphQL breaks standard HTTP caching

Good default: REST for public APIs and simple CRUD. GraphQL only when multiple client types need different data shapes from the same backend.

Section 04

gRPC and RPC

4.1 How It Differs from REST

REST is resource-oriented: you model nouns (events, bookings) and use HTTP verbs on them. RPC is action-oriented: you call functions across a network as if they were local.

Aspect REST gRPC
ParadigmResource-oriented (nouns)Action-oriented (functions)
ProtocolHTTP/1.1 + JSONHTTP/2 + Protocol Buffers (binary)
PerformanceModerateHigh (binary, compressed, multiplexed)
Browser supportNativeRequires grpc-web proxy
ContractOpenAPI or informalStrict .proto file, required
Code generationOptionalRequired, generated clients in any language
StreamingWorkarounds (SSE, WebSocket)Native: unary, server, client, bidirectional
Best forPublic APIs, web and mobile clientsInternal service-to-service communication

4.2 Protocol Buffers (.proto file)

You define your service contract in a .proto file. gRPC generates type-safe client and server code for any language from this single definition.

Proto file example 
syntax = "proto3";

service BookingService {
  // Unary: one request, one response (like REST)
  rpc CreateBooking (BookingRequest) returns (BookingResponse);

  // Server streaming: one request, many responses
  rpc StreamAvailability (EventId) returns (stream TicketUpdate);

  // Bidirectional streaming: many requests, many responses
  rpc Chat (stream Message) returns (stream Message);
}

message BookingRequest {
  string event_id  = 1;    // Field numbers are permanent, never reuse
  string user_id   = 2;
  int32  quantity  = 3;
  string section   = 4;
}

message BookingResponse {
  string booking_id = 1;
  string status     = 2;
}

4.3 When to Use gRPC

  • Interviewer mentions microservices or internal service communication
  • Performance is explicitly a constraint, binary encoding is significantly faster
  • Multiple programming languages in the same system (polyglot)
  • You need streaming between services (live price updates, log streaming)
  • You want compile-time type safety across service boundaries

In practice: use REST for public endpoints consumed by web/mobile clients. Use gRPC for internal service-to-service calls where you control both sides.

Quick Decision Rule: REST or gRPC?

  1. Is this a public API for browsers or third parties? Use REST.
  2. Is this internal communication between services you control? Use gRPC.
  3. Do you need streaming between services? Use gRPC.
  4. Are performance and binary payload size critical? Use gRPC.
  5. Do you need strongly typed contracts across polyglot teams? Use gRPC.
Interview Tip. When the interviewer says "microservices", say: "I would use gRPC between services for performance and type safety, and expose a REST gateway at the edge for external clients." That single sentence shows you understand the internal vs external protocol split, which is the right answer at almost every company.
Extra Interview Tip: field numbers are forever. If you mention gRPC, say "Once a field number is in a .proto file, you never reuse it. Renumbering breaks every deployed client silently. Adding a new field with a fresh number is safe; reusing 5 for a different meaning is a four-hour outage waiting to happen." That answer separates people who have shipped protobufs from people who have only read about them.

What Interviewers Usually Want to Hear

  • You know gRPC is for internal calls, not public APIs
  • You can articulate the performance vs accessibility tradeoff
  • You understand HTTP/2 streaming and why it matters
  • You know the browser needs grpc-web as a proxy

Good default: REST at the edge, gRPC between services. Split by audience, not by preference.

Section 05

Authentication and Authorization

5.1 The Difference

Authentication is who are you. Verifying identity (logging in, presenting credentials).

Authorization is what are you allowed to do. Checking permissions after identity is confirmed.

Always authenticate first, then authorize. They are separate steps.

5.2 JWT Tokens

Best for user-facing web and mobile applications. A JWT is a self-contained token that encodes the user's identity and permissions. Any service with the verification key can validate it without a database lookup.

JWT structure and usage 
# JWT structure: header.payload.signature (base64url encoded)

# Payload contains user context:
{
  "user_id": "123",
  "email":   "john@example.com",
  "role":    "customer",
  "exp":     1734307200          # Expiry timestamp
}

# Sent with every request:
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjoiMTIzIn0.abc123

# Server validates:
# 1. Signature is valid (not tampered)
# 2. Token is not expired
# 3. Claims match the required permissions

Key properties of JWT: stateless, no database lookup needed per request. Short-lived (15 to 60 min) plus refresh token for new access tokens. Any service can verify with the public key.

5.3 API Keys

Best for server-to-server communication and third-party developer access. API keys are long random strings that identify an application, not a user.

API key verification 
# Client sends key in header:
GET /events
Authorization: Bearer sk_live_abc123def456...

# Server verifies:
SELECT client_id, permissions, rate_limit
FROM   api_keys
WHERE  key_hash = hash(received_key)
  AND  revoked = false

When NOT to use API keys: never for end users, users should not manage cryptographic strings. API keys carry no user context, have no expiry by default, and cannot represent individual users.

5.4 Role-Based Access Control (RBAC)

Assign roles to users, assign permissions to roles. In interviews, note which roles can access which endpoints.

Endpoint Customer Manager Admin
GET /eventsYes, allYes, allYes
POST /eventsNoYes, own venueYes
GET /bookings/{id}Own onlyYes, allYes
DELETE /bookings/{id}Own onlyNoYes
GET /reports/revenueNoOwn venue onlyYes

Quick Decision Rule: JWT or API Key?

  1. Is the caller an end user with a login? Use JWT.
  2. Is the caller a server or third-party developer? Use API Key.
  3. Does the system need to know which user made the request? Use JWT.
  4. Does the system only need to know which app made the request? Use API Key.
  5. Do you need both user identity and app context? Use JWT plus an app-level API key in the same request.
Interview Tip. When asked about auth, do not just say "use JWT". Say "I would use short-lived JWTs (15 minutes) for user identity, refresh tokens stored in HTTP-only cookies for session continuity, and API keys for server-to-server calls between my own services. Authorization happens in a separate middleware that checks roles from the JWT claims." That answer shows you understand the full auth picture, not just one token type.
Extra Interview Tip: never trust the user ID from a request. Say "For GET /bookings/456, the JWT gives me the user ID. Before I return the booking, I check whether booking 456 actually belongs to that user. Never trust the user-provided ID in the path." That single line shows you understand authorization as a check on every request, not a one-time login event.

What Interviewers Usually Want to Hear

  • You separate authentication from authorization
  • You know when JWT fits and when API keys fit
  • You think about token expiry and refresh
  • You check ownership on every request, not just at login

Good default: short-lived JWT for users, API keys for services, role checks on every protected request, ownership verified before returning user data.

Section 06

Pagination

Always include pagination on list endpoints. Returning millions of records in one response is a design failure. Use one of these three approaches:

Type How It Works Use When
Offset ?offset=40&limit=20 Simple admin dashboards, no real-time data
Cursor ?cursor=eyJpZCI6NDB9&limit=20 Feeds, timelines, high-volume data
Keyset ?after_id=123&after_date=2024-01-01 Large datasets, production systems
Cursor response shape 
{
  "data": [ { "id": 1, ... }, { "id": 2, ... } ],
  "pagination": {
    "next_cursor":  "eyJpZCI6MjB9",    # Encode the last-seen ID or timestamp
    "has_next":     true,
    "total_count":  1547
  }
}

# Next page request:
GET /events?cursor=eyJpZCI6MjB9&limit=20

Quick Decision Rule: Which Pagination?

  1. Small dataset, admin dashboard, users need to jump to page 47? Use offset.
  2. Large dataset, infinite feed, new items arriving constantly? Use cursor.
  3. Production system with millions of rows and stable sort order? Use keyset.
  4. Never use offset on a table where rows are inserted frequently.
Interview Tip. When asked about pagination, mention the failure mode. Say "I would use cursor pagination, not offset, because offset breaks when new items are inserted between page 2 and page 3. The user would see the same item twice or skip an item entirely. Cursor on a unique, monotonic key avoids that." That answer shows you have shipped this in production, not just read about it.
Extra Interview Tip: cursors must be opaque. Never expose the internal ID or timestamp in the cursor. Encode it with base64 so clients cannot guess ?cursor=123 and read records they did not pay for. If the cursor is reversible, it is a security bug.

What Interviewers Usually Want to Hear

  • You know why offset fails on real-time data
  • You can explain cursor pagination as a stable alternative
  • You keep cursors opaque to prevent enumeration attacks
  • You always include a has_next or equivalent signal so clients know when to stop

Good default: cursor pagination on a unique, monotonic key, with an opaque encoded cursor and a has_next flag in the response.

Section 07

API Versioning

APIs change over time. Versioning lets you evolve your API without breaking existing clients.

Strategy Format Best For
URL Path (recommended) /v1/events then /v2/events Explicit, easy to route, easy to test in browser
Header API-Version: 2 Clean URLs, follows HTTP standards
Query Parameter /events?version=2 Simple to add without new routes
Content Type Accept: application/vnd.api.v2+json Purist REST approach

Quick Decision Rule: Which Versioning Strategy?

  1. Public API for thousands of unknown third-party developers? Use URL path versioning.
  2. Internal API where the team controls every client? Use header versioning.
  3. You have a single client and want minimum ceremony? Use query parameter versioning.
  4. You need content negotiation across multiple formats? Use content type versioning.
  5. Default to URL path when in doubt. It is the most boring choice and that is exactly what you want.
Interview Tip. If the interviewer asks about versioning, you can also say "I would not version the API unless there is a breaking change. Adding fields, adding endpoints, and supporting new parameters are all backwards-compatible. I would only bump the version when I need to remove or rename something." That answer shows maturity. Most teams over-version out of fear.
Extra Interview Tip: the real cost of versioning is the maintenance tax. Say "Running /v1 and /v2 in production means I am paying double for monitoring, security patches, and bug fixes. I would only fork the version when the breaking change is real, and I would give /v1 an explicit sunset date so it can be turned off." That shows you understand versioning is a business decision, not just a technical one.

What Interviewers Usually Want to Hear

  • You default to URL path versioning for clarity
  • You know that adding fields is backwards-compatible and does not need a new version
  • You give old versions an explicit sunset date
  • You understand versioning has a real maintenance cost

Good default: URL path versioning, only when there is a breaking change, with a sunset date for the old version.

Section 08

Rate Limiting

Protects your system from abuse, scraping, and accidental overuse. Implement at the API gateway level.

8.1 Common Strategies

Strategy How It Works Best For
Fixed Window Count requests per fixed time window (e.g., 1000/hour). Resets at boundary. Simple implementation, predictable
Sliding Window Rolling window of the last N seconds. No burst at boundary. Smoother limiting, more accurate
Token Bucket Bucket refills at fixed rate. Allows controlled bursts up to bucket size. Allows legitimate traffic bursts
Leaky Bucket Requests queue and are processed at a fixed rate. Smooths bursty traffic. Strict, even output rate

8.2 Response Headers and Status Code

Rate limit response example 
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit:     1000          # Your limit
X-RateLimit-Remaining: 0             # How many left
X-RateLimit-Reset:     1672531200    # Unix timestamp when limit resets
Retry-After:           60            # Seconds until retry is safe

Typical limits: 1000 requests/hour per authenticated user, 100 requests/hour per IP (unauthenticated), 10 requests/minute for sensitive endpoints like POST /bookings.

Quick Decision Rule: Which Rate Limit Strategy?

  1. Simple internal API, abuse prevention is the only goal? Use fixed window.
  2. Public API, users complain about bursts at the top of the hour? Use sliding window.
  3. API that needs to allow short bursts but block sustained overuse? Use token bucket.
  4. Backend that needs a strict, even output rate? Use leaky bucket.
Interview Tip. When asked about rate limiting, do not just name a strategy. Say "I would start with a fixed window per user for simplicity, then upgrade to token bucket if I see burst problems. The implementation lives at the API gateway, not in the application code, so individual services do not need to think about it." That answer shows you ship the simple thing first and refactor when needed.
Extra Interview Tip: rate limits belong in the response headers, not just the policy. If a client gets a 429 with no Retry-After header, they have to guess when to retry. Good APIs tell the client exactly when to come back. The headers are part of the API contract.

What Interviewers Usually Want to Hear

  • You put rate limiting at the gateway, not in app code
  • You know the tradeoff between fixed window (simple) and sliding window (accurate)
  • You return 429 with Retry-After and rate limit headers
  • You have different limits for different endpoint types

Good default: fixed window per user at the API gateway, 1000/hour for reads, 10/minute for writes, return 429 with Retry-After.

Section 09

Security Checklist

9.1 Input Validation

  • Validate and sanitize all input, type, length, format, range
  • Reject unexpected fields, do not pass raw input to your database
  • Validate on the server, never trust client-side validation alone

9.2 Transport and Data

  • Always use HTTPS, never expose endpoints over plain HTTP
  • Never log sensitive data, no passwords, card numbers, tokens in logs
  • Hash API keys before storing, never store plain text secrets

9.3 Auth and Access

  • Validate JWT signature and expiry on every request
  • Never trust user-provided IDs without checking ownership (e.g. GET /bookings/456, does the caller own booking 456?)
  • Apply the principle of least privilege, grant minimum permissions needed
  • Use short-lived access tokens (15 to 60 min) and refresh tokens

9.4 Infrastructure

  • Rate limit all public endpoints to prevent abuse and DDoS
  • Set CORS headers to restrict which origins can call your API
  • Return generic error messages to clients, do not expose stack traces or internal details

Quick Security Audit: Walk This List Before Every Deploy

  1. All inputs validated server-side? No raw strings into SQL or shell.
  2. HTTPS enforced everywhere? No HTTP fallback, no mixed content.
  3. Sensitive data scrubbed from logs? No tokens, no card numbers, no passwords.
  4. Auth checked on every request? Including the ones that feel internal.
  5. Ownership verified before returning user data? Every query, every time.
  6. Rate limits live at the gateway? Per user, per endpoint type.
Interview Tip. When asked about security, do not just list items. Say "My default posture is deny by default. Every endpoint requires auth, every input is validated, every response is sanitized, every secret is hashed. I would rather spend an hour hardening than spend a day explaining a breach." That answer shows you treat security as the default, not an afterthought.
Extra Interview Tip: the most common security bug is the IDOR. Say "Insecure Direct Object Reference is when GET /users/123 returns any user's data because the endpoint only checks authentication, not authorization. The fix is one line, but it is the line most teams forget." That answer shows you have seen real production bugs, not just read OWASP.

What Interviewers Usually Want to Hear

  • You treat security as deny-by-default, not bolt-on
  • You validate on the server, never trust the client
  • You check ownership, not just authentication
  • You know IDOR is the most common API security bug

Good default: HTTPS everywhere, server-side validation, ownership checks on every read, hashed secrets, no sensitive data in logs, rate limits at the gateway.

Section 10

Real-Time Patterns

Standard REST APIs are request/response. When you need the server to push data, you need a different approach.

Pattern Direction Protocol Best For
WebSocket Both (full-duplex) ws:// Chat, games, collaborative editing
SSE Server to Client HTTP text/event-stream Live notifications, dashboards, feeds
Long Polling Server to Client HTTP Simple notifications, legacy support
Short Polling Client polls server HTTP When real-time is a nice-to-have
Server-Sent Events (SSE) example 
# Server (Node.js):
res.setHeader("Content-Type", "text/event-stream");
res.setHeader("Cache-Control", "no-cache");
setInterval(() => {
  res.write(`data: ${JSON.stringify({ price: getPrice() })}\n\n`);
}, 1000);

# Client:
const es = new EventSource("/prices/AAPL");
es.onmessage = (e) => updateDisplay(JSON.parse(e.data));

Quick Decision Rule: Which Real-Time Pattern?

  1. Real-time is nice-to-have, not critical? Use short polling.
  2. Server only needs to push updates, no client messages? Use SSE.
  3. Both sides need to send messages in real time? Use WebSocket.
  4. Legacy systems that cannot do WebSocket or SSE? Use long polling.
Interview Tip. When asked about real-time, name the tradeoff first. Say "WebSocket is the most powerful but the most expensive to operate. SSE is one-way and uses plain HTTP, so it works through any proxy. Short polling is the simplest and the cheapest. I would start with short polling, upgrade to SSE when latency matters, and only reach for WebSocket when the client also needs to push data." That progression shows you ship the simple thing first.
Extra Interview Tip: SSE is criminally underused. Most engineers jump to WebSocket because it is more famous. But if the server is the only one talking (notifications, live feeds, dashboards), SSE does the job over plain HTTP, works through every proxy, and reconnects automatically on disconnect. Reach for WebSocket only when the client needs to push back.

What Interviewers Usually Want to Hear

  • You know the difference between WebSocket and SSE
  • You can articulate why you would pick one over the other
  • You understand the operational cost of keeping persistent connections alive
  • You start simple and only reach for WebSocket when justified

Good default: short polling for non-critical updates, SSE for one-way server push, WebSocket only when both sides need real-time communication.

Section 11

Interview Quick Reference

Time Allocation

Spend at most 5 minutes on API design. Show judgment and move on. Interviewers lose marks for candidates who get bogged down here instead of discussing architecture.

What to Cover (in order)

  • State your protocol choice: "I will use REST APIs here"
  • List your key endpoints, 3 to 6 is enough
  • Mention authentication: "endpoints are secured with JWT"
  • Mention pagination on list endpoints
  • Move on to high-level design

What to Skip (unless asked)

  • Exact status codes, say "2xx for success, 4xx for client error"
  • Versioning, only mention if the interviewer raises it
  • Detailed rate limiting algorithms
  • Complete request/response schemas

Signal Words and Your Response

If the interviewer says Your response
Over-fetching or under-fetchingMention GraphQL and explain why it fits
Microservices or internal service communicationConsider gRPC for those internal calls
Real-time, live, notificationsMention WebSocket or SSE and explain the tradeoff
Millions of users or scaleEnsure pagination, rate limiting, and auth are mentioned
Mobile and web clients need different dataGraphQL is the right answer here
Third-party developers or public APIREST with API keys, versioning, and rate limiting

Quick Decision Rule: The 5-Minute API Answer

Structure every API design answer in this order so you do not run out of time:

  1. Protocol (30 seconds): "REST, with one path where I add WebSocket."
  2. Endpoints (90 seconds): List 3 to 6. Resource, method, brief purpose.
  3. Auth (45 seconds): "JWT for users, API keys for services."
  4. Pagination (30 seconds): "Cursor on list endpoints."
  5. Rate limiting (30 seconds): "Fixed window per user at the gateway."
  6. Hand off to the next topic (15 seconds): "That covers the API surface, I would like to move on to the data model."
Interview Tip. The single biggest differentiator between senior and junior candidates in system design is the ability to stop talking about API design and move on. Most candidates burn 15 minutes explaining the API and have 5 minutes left for the actual architecture. State the API surface in 3 to 5 minutes and spend the rest on data model, scaling, and tradeoffs. The API is the table of contents; the architecture is the book.
Extra Interview Tip: have one prepared sentence for every signal word. Memorize a one-sentence answer for over-fetching, microservices, real-time, scale, mobile and web, and public API. In the interview, you will not have time to think. You will have time to remember. A memorized sentence that names the tradeoff is worth more than a five-minute improvised explanation.

What Interviewers Usually Want to Hear

  • You made a decision without over-engineering
  • You named the tradeoff behind each choice
  • You moved on to the architecture after 3 to 5 minutes
  • You asked one clarifying question before designing the API

Good default: REST for the surface, JWT for users, cursor pagination, rate limits at the gateway, then move on to the part of the system that actually matters.
