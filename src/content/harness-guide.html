Harness Design

Harness 101

Most people try to make AI smarter with better prompts. The bigger upgrade is giving the model a better environment to work inside. That environment is your harness.

Build a basic Claude Code harness and ship it today. By the end of this guide, you will have a working version 0.1 on disk, plus a clear ladder for what to improve once it starts saving you real work.

Step 01

Start smaller than you think

Your first harness does not need 10 agents, 15 MCP servers, a vector database, autonomous workflows, or complicated memory infrastructure. It needs three things: 1 context file, 1 skill, 1 tool. That is enough to feel the difference.

The Minimum Viable Harness

What What It Does Why It Matters
CONTEXT.mdTells the model who you are, how you work, what to never doThe model is no longer starting from zero on every prompt
1 skillTeaches the model how to perform one task you do repeatedlyYou stop rewriting the same instructions for the same task
1 toolConnects the model to one place where real work happensThe model can act, not just answer
The principle. The goal of a version 0.1 harness is not feature completeness. It is to remove one specific kind of friction. The first friction to remove is the one you feel every single day, the same prompt you have typed five times this week. Build for that one.

Common Mistake: Building the "Dream Harness"

Most first attempts fail because they try to design the harness the user wishes they had, not the one they need today. The result is a folder full of half-configured agents and skills, none of which are connected to a real workflow. Smaller beats better. A working version 0.1 you use every day is worth more than a perfect version 0.9 you do not.

What You Will Have Built by the End

  • A my-harness/ folder with CONTEXT.md, one skill, and one project state file
  • One tool connected (pick the one you will actually use this week)
  • One explicit permission boundary in writing
  • A clear sense of what level your harness is at on the 0 to 5 ladder

Step 02

Create your context file

Make a file called CONTEXT.md. Put only information the AI repeatedly needs. The most common beginner mistake is to turn this into a giant biography. More context is not automatically better context. The model has a limited attention budget, and every useless instruction competes with the useful ones.

What Goes In

Four sections, in this order. Nothing more for version 0.1.

CONTEXT.md template 
# About me

I am a frontend developer and tech creator.

## How I work
- I prefer short explanations.
- I like examples before theory.
- I want strong hooks for content.
- Avoid corporate language.

## Current priorities
- AI content
- coding education
- creator workflows

## Rules
- Do not publish anything without approval.
- Ask before spending money.

The "Context as RAM" Mental Model

Think of context like RAM. Load what matters for this task, not your entire life. A good CONTEXT.md is the small set of facts that every task needs. Project-specific details belong in a project file. One-off facts do not belong in the harness at all.

Common mistake: putting the wrong things in context. Two patterns show up in almost every beginner harness. (1) Stuffing the file with "about me" biography content the model never references. If you have not asked the AI to use a fact in three sessions, it is taking up space for no reason. (2) Putting live project state in CONTEXT.md. That belongs in a separate project file, addressed in Step 06.

How to Know It Is Working

Use the harness on three real tasks in the first week. Anything you find yourself explaining again belongs in the file. Anything the AI never uses should probably come out. This is a feedback loop, not a one-time write. Most well-tuned CONTEXT.md files end up shorter, not longer, than the first draft.

Step 03

Add one reusable skill

A skill teaches the AI how you want a task performed. Create a folder for it, then a single SKILL.md inside. The first skill should be a task you do at least once a week, where you have already figured out the steps in your head and just keep re-explaining them.

The Folder Structure

Skill folder 
skills/
  short-form-video/
    SKILL.md

A Real Example: Short-Form Video Skill

SKILL.md example 
# Short Form Tech Video

When creating a tech video:

1. Start with the surprising part.
2. Explain the idea in plain English.
3. Introduce the technical term only after the viewer understands the problem.
4. Keep spoken sentences short.
5. Include one visual example.
6. End with one clear CTA.

Now you do not need to rewrite that workflow every time.

The Context vs Skill Distinction

What Goes In Example
ContextWhat the AI should know about you"I prefer short explanations."
SkillHow the AI should perform a specific task"When writing a video script, start with the surprising part."
Project stateWhere the current work is right now"Script approved, next step is filming, deadline Aug 20."
Common mistake: mixing context and skill into one file. People write "how to do this task" and "who I am" into the same document. The result is a file that has to be loaded on every task, even the ones where only the context part is needed. Keeping them separate lets the system load the right thing at the right time.

Step 04

Give it one tool

Now connect one place where real work happens. Good first options are Google Drive, Gmail, GitHub, the filesystem, or Notion. Pick the one that removes the most repeated copying and pasting from your week, not the one that sounds the most impressive.

What "Good First Tool" Looks Like

  • You currently copy and paste content between this tool and your AI at least three times a week
  • The content inside is text or file-based, not heavy media that needs special handling
  • You are comfortable with the model reading from it. You would not flinch at the words "the AI is going to open my Drive"
  • The tool has a clean MCP or API integration, or a simple file-based alternative

What Changes Once a Tool Is Connected

This is the moment the harness stops being a configuration and starts being a workflow:

A connected flow, in plain text 
YOU
 "make a reel from the latest brand brief"
        |
        v
       AI
        |
 reads Drive     <- tool
        |
 loads skill     <-- skills/short-form-video/SKILL.md
        |
 uses context    <-- CONTEXT.md
        |
        v
 creates draft

That already behaves very differently from a blank chatbot. You are not longer typing context, skill, and instructions into every prompt. They are loaded automatically, and the AI is acting on real content from a real system.

How to Choose Which Tool Comes First

Ask three questions. (1) What content do I copy and paste the most? That is the tool. (2) Which of those tools has the cleanest MCP integration? Pick that one even if it is not the most-used, because a tool that does not connect cleanly is worse than a tool you have to live without. (3) Which one would I trust the AI to read-only first, before giving it write access? Start with read-only access to the highest-traffic tool, and graduate to write access after you have watched how it behaves.

Step 05

Add one guardrail

The moment AI gets tools, you need boundaries. A useful agent is not the one with maximum access. It is the one with the minimum access required to finish the job. That principle becomes much more important as your harness grows.

A Simple Permission Model

Permissions template 
## Permissions

Can do automatically:
- read files
- summarize
- create drafts
- research

Needs approval:
- send emails
- publish content
- delete files
- spend money

The Three Layers of Guardrails

Layer What It Does Example
Written rulesTell the model what it can and cannot do, in plain text in your context or skill file"Do not publish without approval"
Tool-level scopeConfigure each tool integration to allow only the actions you actually wantRead-only Drive access, draft-only Gmail folder
Human checkpointsDefine the exact moments where the model must stop and wait for youBefore any send, publish, delete, or spend action
Common mistake: skipping the written rules. Most people focus on tool-level scope ("I gave the AI read-only access") and skip the written rules. Both are needed. Tool scope is what the system enforces when you are not watching. Written rules are what the model falls back on when it is making a judgment call. The two together is what a real guardrail looks like.

What to Add Later, Not Now

You do not need a full permission framework in version 0.1. You need one written list of what is automatic versus what needs your approval. That single document, attached to the harness, is enough to keep you out of trouble. The bigger permission system comes when you have multiple skills and tools working together, and you need to express more nuanced rules.

Step 06

The maturity ladder

You now have a basic AI harness. Not because it looks complicated. Because the model is no longer starting from zero. The diagram below is what you have actually built.

6.2 The Levels

Level What You Have The Phrase That Describes It
Level 0Chatbot"I prompt it."

Level 2Skills"It knows how I work."
Level 3Tools"It can do things."
Level 4State"It knows where we left off."
Level 5Workflows"It can keep work moving."

6.3 The Subtle Part: Context Engineering

The goal is not permanent memory of everything. The real goal is to give the model the right context at the right moment. This is where harness design starts becoming context engineering. A good system decides three things:

  • What should always be loaded? The small set of facts that every task needs, the CONTEXT.md content
  • What should be retrieved only when relevant? Project state, large reference docs, past decisions
  • What should never enter context at all? One-off facts, old project history, content the model will not reference

This matters because every useless instruction competes with the useful ones. A 500-line context file does not give the model more capability. It gives it less, because the attention budget is now spread across things the task did not need.

6.4 State vs Memory

Another thing beginners usually miss. Your harness should have state. State simply means "what happened already?" For example, a projects/current.md file:

projects/current.md 
# current-project.md

Brand: ExampleAI
Status: script approved
Next step: film
Deadline: August 20

Without state, even a well-designed agent can repeatedly rediscover the same information. Memory tells it who you are. State tells it where the work currently is. Different problem. Different file.

6.5 The Folder You Will Build Today

my-harness/ version 0.1 
my-harness/

CONTEXT.md

skills/
  content/
    SKILL.md

projects/
  current.md

# then connect one tool

That is your version 0.1. Do not automate it yet. Use it manually for several real tasks first. If the same sequence keeps repeating, then turn that sequence into a workflow. Another rule people skip: automate proven behavior, not imagined behavior.

You do not need level 5 on day one. Build level 1 properly first. The maturity ladder is a diagnosis tool, not a to-do list. If you are at level 2, do not skip to level 5 because the diagram looked good. Each level unlocks new failure modes you have not seen yet, and the time to learn them is when your harness is small enough to debug.

Create one CONTEXT.md file today with only the information your AI repeatedly needs. Then use it on three real tasks. Anything you find yourself explaining again belongs in the harness. Anything the AI never uses should probably come out. The harness is a feedback loop, not a one-time write.
