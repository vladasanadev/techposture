Section 01

Why Containers, Not VMs

This is increasingly asked even in non-DevOps interviews, as a filter for "does this candidate understand how their code actually ships." The core idea: containers share the host OS kernel. Virtual machines each run a full, separate OS.

Aspect Virtual Machine Container
What's isolated A full guest OS, including its own kernel Just the process and its filesystem view. Kernel is shared with the host.
Startup time Seconds to minutes. Boots an entire OS. Milliseconds to seconds. Just starts a process.
Size Gigabytes. Includes a full OS. Megabytes to low gigabytes. Just app and dependencies.
Isolation strength Stronger. Separate kernels, harder to escape. Weaker by default. Shared kernel means a kernel exploit can affect the host.
Density Fewer VMs per host. Each carries full OS overhead. Many more containers per host. Minimal per-container overhead.

Quick Decision Rule: Container or VM?

  1. Application workload, web service, microservice? Container.
  2. Strong kernel-level isolation between untrusted tenants? VM.
  3. Need a specific kernel version or custom kernel module? VM.
  4. Stateless service that must boot in under a second? Container, no contest.
Interview Tip. Say "A container is not a lightweight VM. It is just a regular process on the host, isolated using Linux namespaces for what it can see, and cgroups for what resources it can use. There is no hypervisor and no second kernel involved." This is the single sentence that separates candidates who have read a diagram from candidates who understand the mechanism.
Extra Interview Tip: name the two Linux kernel primitives specifically. Say "Namespaces give a process its own isolated view of things like the process list, network interfaces, and filesystem mounts. Cgroups limit and account for what resources, like CPU, memory, and I/O, that process is allowed to use. Docker is really just a friendly interface over both." Most candidates know Docker uses "some kernel magic" but cannot name the two actual mechanisms. Naming them is a clear differentiator.

What Interviewers Usually Want to Hear

  • You know containers share the host kernel; VMs each run their own
  • You can name namespaces and cgroups as the actual underlying mechanisms
  • You know the practical tradeoff: containers are faster and denser, VMs are more strongly isolated

Good default: containers for most application workloads, fast and dense and disposable. VMs when you need strong kernel-level isolation between untrusted tenants.

Section 02

Images and Layers

A Docker image is a read-only template built from a stack of layers. A container is a running instance of an image, with one thin writable layer on top. Understanding layers is what makes Dockerfile ordering make sense instead of feeling arbitrary.

2.1 How Layers Work

Each instruction in a Dockerfile that changes the filesystem (RUN, COPY, ADD) creates a new layer. Layers are cached. If a layer's inputs have not changed, Docker reuses the cached layer instead of rebuilding it. This is why instruction order in a Dockerfile directly affects build speed.

Each layer is cached. Change the top layer, keep everything below it.

2.2 The Caching Rule That Matters Most

Docker invalidates a layer's cache, and every layer after it, the moment anything in that layer's inputs changes. This is why COPY-ing your entire app before installing dependencies is a common performance mistake. Every code change forces a full dependency reinstall.

Dockerfile layer ordering 
# SLOW: any code change invalidates the dependency install layer below it
COPY . .
RUN npm install

# FAST: dependency layer only rebuilds when package.json actually changes
COPY package.json package-lock.json ./
RUN npm install
COPY . .

Quick Decision Rule: Layer Order in a Dockerfile

  1. Least-frequently-changing stuff first. Base image, system packages, then app dependencies.
  2. Most-frequently-changing stuff last. Source code, config files, build artifacts.
  3. Each RUN, COPY, ADD is a new layer. Combine related shell steps in one RUN to keep the layer count down.
Interview Tip. Say "I would copy just the dependency manifest first and install dependencies before copying the rest of the source code, so that layer stays cached across builds unless dependencies actually change. Code edits alone will not trigger a full reinstall." This is the single most practical Dockerfile optimization and interviewers listen for it specifically.
Extra Interview Tip: mention multi-stage builds. Say "For a compiled language, I would use a multi-stage build. One stage with the full compiler toolchain to build the binary, then a second, minimal final stage that only copies the compiled artifact in. That keeps the shipped image small without needing the build tools present in production." This is a real production technique that shows depth beyond a single-stage Dockerfile.

What Interviewers Usually Want to Hear

  • You know an image is layers, a container is a running instance plus a writable layer
  • You order Dockerfile instructions to maximize cache reuse, least-frequently-changing first
  • You know multi-stage builds keep final images small by discarding build-time tooling

Good default: order layers from least to most frequently changing, and use multi-stage builds to keep the shipped image lean.

Section 03

Writing a Good Dockerfile

Beyond layer ordering, there are a handful of concrete practices that separate a Dockerfile that "works" from one that is actually production-appropriate.

Production-style Dockerfile 
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --only=production

FROM node:20-alpine
WORKDIR /app
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
COPY --from=builder /app/node_modules ./node_modules
COPY . .
USER appuser
EXPOSE 3000
HEALTHCHECK CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "server.js"]
Practice Why It Matters
Use a specific, minimal base tag (node:20-alpine, not node:latest)latest is a moving target. Your build is not reproducible and can silently break.
Run as a non-root USERIf the container is compromised, the attacker does not get root inside it. Meaningfully reduces blast radius.
Use .dockerignoreKeeps .git, node_modules, and secrets out of the build context and final image
Prefer COPY over ADDADD has implicit behaviors (auto-extracting archives, fetching URLs) that are easy to trigger by accident
One process per containerKeeps scaling, restarting, and log collection simple and independent per concern
Use HEALTHCHECKLets Docker and orchestrators know the container is actually ready, not just running

Quick Decision Rule: Dockerfile Review Checklist

  1. Base image pinned to a specific version? node:20-alpine, never latest.
  2. Running as a non-root user? Switch with USER, even for simple images.
  3. .dockerignore exists and excludes .git, secrets, build artifacts?
  4. Dependency layer separated from source layer? Manifest first, install, then code.
Interview Tip. If asked to review a Dockerfile, check these first, out loud: "Is the base image pinned to a specific version? Is it running as a non-root user? Is there a .dockerignore? Is the dependency-install layer separated from the code-copy layer for caching?" A checklist answer like this reads as someone who has actually shipped containers to production, not someone reciting Docker syntax.
Extra Interview Tip: mention distroless or scratch for the security extra mile. Say "For a compiled binary with no runtime dependencies, I could go even further than Alpine and use a distroless or scratch base image. No shell, no package manager, nothing an attacker could use even if they got code execution inside the container." This is genuinely advanced and rarely mentioned unprompted.

What Interviewers Usually Want to Hear

  • You pin base image versions instead of using latest
  • You run as a non-root user by default
  • You use .dockerignore and prefer COPY over ADD
  • You know HEALTHCHECK exists and what problem it solves

Good default: pinned minimal base image, non-root user, .dockerignore, dependency layer cached separately from code, one process per container.

Section 04

Containers, Volumes and Networking

A container's writable layer disappears the moment the container is removed. This surprises people who expect files written inside a container to persist. They do not, unless you explicitly opt in with a volume.

4.1 Volumes: Where Persistent Data Actually Lives

Type What It Is Use For
Named Volume Docker-managed storage, lives outside any single container's lifecycle Databases, anything that must survive container removal
Bind Mount Maps a specific host directory directly into the container Local development. Edit code on the host, see changes live in the container.
tmpfs Mount In-memory only, never touches disk Sensitive temporary data that should not persist anywhere
Volume types in docker run 
docker run -v mydata:/var/lib/postgresql/data postgres     # named volume
docker run -v $(pwd):/app node:20                            # bind mount, local dev
docker run --tmpfs /tmp/secrets alpine                        # in-memory only

4.2 Docker Compose for Local Multi-Container Setups

docker-compose.yml 
services:
  web:
    build: .
    ports: ["3000:3000"]
    depends_on: [db]
  db:
    image: postgres:16
    volumes: ["dbdata:/var/lib/postgresql/data"]
    environment:
      POSTGRES_PASSWORD: local_dev_only
volumes:
  dbdata:

Compose defines a private network automatically. Services reach each other by service name (db, not an IP address), which is exactly how Kubernetes Services will behave later, so Compose is a genuinely useful mental model bridge.

Quick Decision Rule: Which Volume Type?

  1. Data that must survive container removal? Named volume.
  2. Local development with live code reload? Bind mount.
  3. Sensitive temporary data, must never hit disk? tmpfs mount.
  4. Anything else? You probably do not need a volume. Default to ephemeral.
Interview Tip. If asked why a container "lost its data" after a restart, say "Anything written to the container's own writable layer is gone the moment the container is removed. It needs to be in a named volume to persist. This is one of the most common surprises for people new to Docker, expecting the container to behave like a persistent VM."
Extra Interview Tip: depends_on does not mean readiness. Say "depends_on in Compose controls startup order, not readiness. My app container might start before Postgres is actually accepting connections. I would add a retry loop in the app's startup, or a proper healthcheck-based wait, rather than assuming depends_on alone guarantees the database is ready." This is a real bug people hit constantly and rarely explain correctly.

What Interviewers Usually Want to Hear

  • You know a container's own filesystem is ephemeral without an explicit volume
  • You can distinguish named volumes, bind mounts, and tmpfs by use case
  • You know depends_on controls start order, not readiness

Good default: named volumes for anything that must persist, bind mounts for local dev only, and never assume startup order implies readiness.

Section 05

Why Kubernetes

Docker runs one container. Kubernetes runs a fleet of containers across many machines, and keeps them running the way you declared, even as individual machines fail. The mental shift: you do not tell Kubernetes what to do step by step. You declare the desired end state, and a control loop continuously works to make reality match it.

5.1 The Problem Kubernetes Actually Solves

  • Scheduling: deciding which machine runs which container, based on available resources
  • Self-healing: if a container crashes or a machine dies, Kubernetes restarts or reschedules it automatically
  • Scaling: adding or removing container instances based on load, without manual intervention
  • Service discovery: containers can find and talk to each other by stable names, even as individual instances come and go
  • Rolling updates: deploying a new version gradually, with automatic rollback if it starts failing

Quick Decision Rule: When Is Kubernetes Worth It?

  1. One service on one machine? Docker Compose is enough. Skip Kubernetes.
  2. A few services, manual deploys, predictable load? Docker Compose or a single-host setup.
  3. Many services, autoscaling, zero-downtime deploys, multi-node? Kubernetes pays off.
  4. Need scheduled batch jobs and long-running services in one cluster? Kubernetes.
Interview Tip. Say "Kubernetes is a declarative control loop. I describe the desired state, like 'run 3 replicas of this container,' and Kubernetes continuously reconciles actual state to match it. If a pod dies, the control loop notices the mismatch and starts a new one. I do not write that recovery logic myself." "Declarative control loop" is the specific phrase that signals real understanding versus memorized object names.
Extra Interview Tip: distinguish build tool from orchestrator. Say "Kubernetes does not build or run containers itself directly. It orchestrates them via a container runtime, like containerd. Docker is one way to build the images. Kubernetes is a separate layer deciding where and how many of those images actually run." This distinction, build tool vs orchestrator, is commonly blurred by candidates who have only used Docker locally.

What Interviewers Usually Want to Hear

  • You describe Kubernetes as declarative: desired state plus a reconciling control loop
  • You can name the concrete problems it solves: scheduling, self-healing, scaling, discovery, rollout
  • You know Kubernetes and Docker solve different problems, not the same problem at different scale

Good default: declare desired state, let the control loop reconcile it. Do not think in terms of imperative commands once you are on Kubernetes.

Section 06

Core Objects: Pods, Deployments, Services

Three objects cover most of what comes up in an interview. Learn them in this order. Each one wraps and manages the one before it.

Object What It Is Key Fact
Pod The smallest deployable unit. One or more containers that share network and storage. Pods are disposable and do not self-heal on their own. You almost never create one directly.
Deployment Manages a set of identical pod replicas, handles rollouts and self-healing This is what you actually create in practice, not a bare Pod
Service A stable network identity and load balancer in front of a changing set of pods Pods get new IPs constantly as they are recreated. Services give you a fixed address that does not change.
Deployment + Service, the canonical pair 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api
spec:
  replicas: 3
  selector:
    matchLabels: { app: checkout-api }
  template:
    metadata:
      labels: { app: checkout-api }
    spec:
      containers:
        - name: checkout-api
          image: myregistry/checkout-api:1.4.2
          ports: [{ containerPort: 3000 }]
---
apiVersion: v1
kind: Service
metadata:
  name: checkout-api
spec:
  selector: { app: checkout-api }
  ports: [{ port: 80, targetPort: 3000 }]

Quick Decision Rule: Which Object to Create

  1. Stateless service that should self-heal and roll out? Deployment.
  2. Need a stable address and load balancing in front of a set of pods? Service.
  3. Database or anything that needs a stable network identity and persistent storage? StatefulSet, not Deployment.
  4. Need one pod per node for logging or monitoring? DaemonSet.
Interview Tip. Say "I never create bare Pods in practice. I define a Deployment, which manages a ReplicaSet, which ensures the desired number of Pods are always running and handles rolling updates. In front of that I would put a Service, since Pod IPs change every time a Pod is recreated, and I need something stable to route traffic to." This three-object chain, said fluently, is the single most-tested piece of Kubernetes knowledge.
Extra Interview Tip: labels and selectors are the actual glue. Say "There is no hardcoded link between a Deployment and a Service. They are connected purely by label selectors. The Service selects any Pod with a matching label, which is what lets me swap which Pods receive traffic just by changing labels, without touching the Service definition at all." Understanding labels as the connective tissue, rather than memorizing YAML shape, is what actually lets you debug a broken cluster.

What Interviewers Usually Want to Hear

  • You know the Deployment to ReplicaSet to Pod chain and why each layer exists
  • You know Pods get new IPs on recreation, which is exactly why Services exist
  • You understand labels and selectors as the actual connective mechanism, not magic linking

Good default: Deployment for the desired state and self-healing, Service for a stable network identity, labels as the glue connecting them.

Section 07

Kubernetes Networking

Every Pod gets its own IP, and any Pod can reach any other Pod directly by default, without NAT. Services exist on top of this to solve the problem of Pod IPs being unstable, and to distribute traffic across multiple matching Pods.

7.1 Service Types

Type What It Does Use For
ClusterIP (default) A stable internal-only IP, reachable only inside the cluster Internal service-to-service communication. Most Services are this type.
NodePort Exposes the Service on a static port on every node's own IP Simple external access, mostly for development or testing, rarely production
LoadBalancer Provisions an actual external load balancer via the cloud provider Production external access to a Service
Ingress Not technically a Service type. An HTTP(S) router in front of multiple Services, handling routing rules, TLS, and hostnames. Exposing many Services under one external IP with path or host-based routing

Quick Decision Rule: Which Service Type?

  1. Internal service-to-service call, no external access? ClusterIP. Default.
  2. Quick external access for dev or testing? NodePort.
  3. One production service needing its own external IP? LoadBalancer.
  4. Many services behind one external IP, HTTP(S) routing? Ingress.
Interview Tip. Say "For internal traffic between services I would use the default ClusterIP. For external access, I would generally reach for an Ingress rather than a separate LoadBalancer Service per app, since Ingress lets me route multiple services under one external IP and handle TLS termination in one place instead of provisioning a cloud load balancer for every single service." Naming Ingress specifically, and why it is usually preferred over one LoadBalancer per service, is a strong cost-awareness signal.
Extra Interview Tip: DNS-based service discovery. Say "Kubernetes runs an internal DNS server, so a Pod can reach another Service just by its name, like http://checkout-api, or the fully qualified checkout-api.default.svc.cluster.local across namespaces. I never hardcode Pod IPs, since they are not stable anyway." This is the mechanism that actually makes microservice-to-microservice calls work, and it is often glossed over as "magic."

What Interviewers Usually Want to Hear

  • You know ClusterIP is the default and correct choice for internal traffic
  • You know Ingress is generally preferred over per-service LoadBalancers for cost and routing flexibility
  • You know service discovery happens via internal DNS by service name, never hardcoded IPs

Good default: ClusterIP internally, Ingress for external HTTP(S) traffic across multiple services, DNS names instead of hardcoded IPs everywhere.

Section 08

Health Probes and Scaling

Kubernetes cannot know whether your application is actually healthy unless you tell it how to check. This is where "how would you deploy this" system design questions frequently go once the basic objects are covered.

8.1 Liveness vs Readiness Probes

Probe Question It Answers Failure Response
Liveness "Is this container still functioning, or is it stuck or deadlocked?" Kubernetes restarts the container
Readiness "Is this container ready to accept traffic right now?" Kubernetes stops sending it traffic, but does NOT restart it
Startup "Has this container finished its (possibly slow) initial startup?" Delays liveness and readiness checks until startup succeeds, preventing a slow-starting app from being killed prematurely
Probe configuration 
livenessProbe:
  httpGet: { path: /health, port: 3000 }
  initialDelaySeconds: 10
  periodSeconds: 15
readinessProbe:
  httpGet: { path: /ready, port: 3000 }
  initialDelaySeconds: 5
  periodSeconds: 10

8.2 Scaling: HPA

A HorizontalPodAutoscaler (HPA) automatically adjusts the number of pod replicas based on observed metrics, most commonly CPU or memory utilization, though custom metrics (queue depth, request latency) are also supported.

HorizontalPodAutoscaler 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: checkout-api-hpa }
spec:
  scaleTargetRef: { kind: Deployment, name: checkout-api }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

Quick Decision Rule: Liveness, Readiness, or Startup?

  1. Process is hung or deadlocked and only a restart will fix it? Liveness.
  2. Process is alive but cannot serve traffic yet (warming up, DB reconnecting)? Readiness.
  3. App takes a long time to start (JVM, large import)? Startup probe, to prevent liveness from killing it during boot.
  4. Default for most services? Liveness on a lightweight endpoint, readiness on a dependency-aware endpoint, startup for slow boots.
Interview Tip. Say "I would add both a liveness probe hitting a lightweight health endpoint, and a separate readiness probe that also checks downstream dependencies like the database connection. The pod is only marked ready once it can genuinely serve a request, not just once the process has started." Distinguishing what each probe checks, not just that both exist, is the actual signal.
Extra Interview Tip: CPU is often the wrong scaling signal. Say "For a queue-processing service, CPU utilization is often a poor scaling signal. I would scale on queue depth instead, using a custom metrics adapter, since a service can be CPU-idle while still falling behind on a growing backlog." This shows you think about the actual bottleneck, not just reach for the default HPA config.

What Interviewers Usually Want to Hear

  • You know liveness restarts, readiness only removes from traffic, and why that distinction matters
  • You know startup probes exist for slow-starting apps to avoid premature restarts
  • You know HPA can scale on custom metrics, not just CPU, when CPU is not the real bottleneck

Good default: lightweight liveness probe, dependency-aware readiness probe, startup probe for slow boots, and scale on the metric that actually reflects load.

Section 09

Config, Secrets and Storage

Containers should be built once and configured per environment, not rebuilt for each one. Kubernetes gives you two objects for exactly this, plus a storage abstraction for anything that needs to persist.

Object What It Holds Key Fact
ConfigMap Non-sensitive configuration. URLs, feature flags, log levels. Stored in plain text, visible to anyone with cluster read access
Secret Sensitive data. Passwords, API keys, TLS certs. Base64-encoded by default, which is encoding, not encryption. Treat this as a common security trap.
PersistentVolume / PersistentVolumeClaim Durable storage that outlives any individual Pod A Pod's own filesystem is ephemeral, exactly like a plain Docker container. PVs are the Kubernetes-level fix.

Quick Decision Rule: ConfigMap vs Secret vs PV

  1. Non-sensitive config that varies by environment? ConfigMap.
  2. Passwords, API keys, TLS certs? Secret, ideally backed by an external secrets manager.
  3. Data that must survive a pod restart (DB files, uploads)? PersistentVolume + PersistentVolumeClaim.
  4. Highly sensitive secrets? Mount as a file, not an env var, to reduce leak surface.
Interview Tip. Say "I would put non-sensitive config in a ConfigMap and sensitive values in a Secret, injected as environment variables or mounted files rather than baked into the image. That lets the same image run across dev, staging, and production with different config, without rebuilding it per environment." "Build once, configure per environment" is the actual principle interviewers are checking for.
Extra Interview Tip: mount Secrets as files, not env vars, for sensitive credentials. Say "Environment variables can leak more easily, through crash dumps, logs, or child processes inheriting them. For highly sensitive values, I would mount the Secret as a file instead, which is a narrower exposure surface, and pair it with a tool like Vault Agent for automatic rotation." This env-var-vs-file distinction for secrets is a real production concern most candidates never mention.

What Interviewers Usually Want to Hear

  • You separate ConfigMaps (non-sensitive) from Secrets (sensitive) by default
  • You know base64 is encoding, not encryption, and name a real mitigation
  • You know Pod storage is ephemeral and PersistentVolumes are the fix, same as Docker volumes

Good default: build the image once, inject environment-specific config via ConfigMaps and Secrets, never trust base64 alone to protect sensitive values.

Section 10

Common Mistakes and Pitfalls

The gap between "I know Docker and Kubernetes commands" and "I have actually run this in production" shows up almost entirely in this list.

Symptom Likely Cause Fix
Container works locally, fails in the cluster No resource requests or limits set. Pod gets scheduled onto a node without enough actual capacity, or gets OOM-killed. Always set CPU and memory requests and limits on every container
Deployment update takes down the app briefly No readiness probe, or rollout strategy is not configured. Traffic hits Pods before they are ready. Add a real readiness probe and use a RollingUpdate strategy with maxUnavailable tuned appropriately
"Works on my machine" image behaves differently in production Base image tag drifted (:latest), or environment-specific config baked into the image Pin exact image digests or tags, externalize all config via ConfigMaps and Secrets
Pod restarts repeatedly (CrashLoopBackOff) App crashes on startup, often from missing config, a failing dependency, or an over-aggressive liveness probe kubectl logs and kubectl describe pod first. Do not guess, read the actual failure.
Secrets visible in kubectl output or CI logs Secrets echoed in build logs, or base64 mistaken for real protection Never log Secret values, enable etcd encryption at rest, consider an external secrets manager
Cluster costs balloon unexpectedly Over-provisioned resource requests, or a LoadBalancer Service per app instead of shared Ingress Right-size requests based on actual usage, consolidate external access behind Ingress

Quick Decision Rule: The Production-Readiness Checklist

  1. Resource requests and limits set on every container?
  2. Liveness and readiness probes both present, checking the right things?
  3. Rolling update strategy with sensible maxUnavailable and maxSurge?
  4. External traffic going through Ingress, not one LoadBalancer per service?
  5. Secrets backed by an external manager, not just base64 in YAML?
Interview Tip. When describing any deployment, narrate production-readiness as you go, not after being asked: "I would set resource requests and limits so the scheduler places this sensibly and it cannot starve other pods, add a readiness probe so it only receives traffic once actually ready, and use RollingUpdate so deploys do not cause downtime." Saying this proactively is worth more than a technically complete YAML file with none of it mentioned out loud.
Extra Interview Tip: the mistake that actually costs interview points. It is rarely picking the wrong Service type. It is forgetting resource requests, resource limits, and health probes entirely when sketching a deployment. These are treated as baseline production-readiness, the same way indexing is baseline for a database design answer. An interviewer sketching a "deploy this" scenario is almost always listening for whether you mention these unprompted, not whether you can recite every field in a Deployment spec from memory.

What Interviewers Usually Want to Hear

  • You mention resource requests and limits and health probes without being prompted
  • You debug with kubectl logs and kubectl describe pod first, rather than guessing
  • You know CrashLoopBackOff means "investigate the actual failure," not "restart harder"
  • You treat base64 Secrets and default configs as things to actively question, not trust

Good default: resource limits, health probes, and RollingUpdate are baseline for every deployment. Narrate them unprompted, and debug from actual logs, never guesses.

Section 11

Interview Quick Reference

Time Allocation

In a system design interview, deployment and infra questions usually come at the end, in 3 to 5 minutes, once the API and data layer are settled. Keep the answer tight: containerize, orchestrate, expose, observe, in that order.

What to Cover (in order)

  • Containerize the app with a minimal, pinned, non-root Dockerfile
  • Deploy it via a Kubernetes Deployment with resource requests and limits set
  • Add liveness and readiness probes. Say what each one actually checks.
  • Expose it via a Service (ClusterIP internally, Ingress for external HTTP)
  • Mention autoscaling on the metric that reflects real load, and rolling updates for zero-downtime deploys

Signal Words and Your Response

If the interviewer says Your response
"How would you deploy this"Dockerize, Deployment + Service, probes, resource limits, Ingress for external traffic
"Zero-downtime deploys"RollingUpdate strategy, readiness probes so new pods only get traffic once actually ready
"Handle traffic spikes"HorizontalPodAutoscaler, scaled on the metric that reflects the real bottleneck
"Store secrets" or "API keys"Kubernetes Secret, mounted as a file, ideally backed by an external secrets manager
"Persist data" (database, uploads)PersistentVolume and PersistentVolumeClaim, never rely on a Pod's own ephemeral filesystem
"Multiple services, one domain"Ingress with path or host-based routing, not one LoadBalancer per service

Quick Decision Rule: The Deployment Answer

  1. Containerize (10s): "Minimal pinned base image, non-root user, multi-stage build if compiled."
  2. Orchestrate (15s): "Deployment with N replicas, resource requests and limits set."
  3. Health (10s): "Readiness probe checks dependencies, liveness probe is lightweight and separate."
  4. Expose (10s): "ClusterIP internally, Ingress for external HTTP with TLS termination."
  5. Scale (10s): "HPA on the metric that actually reflects load, not CPU by default if that is not the bottleneck."
Interview Tip. Have one specific incident story ready: a CrashLoopBackOff you debugged, a bad rollout you rolled back, a resource limit you had to tune. The pattern-matching table above gets you through the knowledge check. One real story is what makes the DevOps portion of an interview memorable rather than just correct.
Extra Interview Tip: name the build-once principle. Say "The image should be built once and promoted through dev, staging, and production unchanged. Anything that varies per environment, like config, secrets, and feature flags, is injected at runtime, not baked into the image." That single principle, said once, signals you have shipped containers the way mature teams actually ship them, not just the way a tutorial does.

What Interviewers Usually Want to Hear

  • You covered containerize to orchestrate to expose to scale in a tight, ordered answer
  • You mentioned resource limits and health probes without being asked specifically
  • You know Ingress over per-service LoadBalancers, and PersistentVolumes over ephemeral Pod storage
  • You have one real debugging story ready, not just definitions

Good default: containerize with a lean, non-root, pinned image. Deploy with resource limits and real health probes. Expose via Ingress. Scale on the metric that matches actual load.
